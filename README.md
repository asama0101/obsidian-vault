# Obsidian vault 構成

タスク管理・メモ・議事録など業務全体を1つのvaultで管理するための構成。`type`プロパティでBasesを絞り込むため、ノートをどのフォルダに置いても正しく集計される。

人間が触るのは`Inbox/`・`Review/`・`Today.md`（の`## メモ`欄）だけで、それ以外（`Cabinet/`配下）はClaude Codeが専管する。Obsidianコア機能（Bases・全文検索・テンプレート）に加え、日々の操作と検出をClaude Codeに委譲する（詳細は`.claude/CLAUDE.md`を参照）。役割分担の詳細は後述の「役割分担」節を参照。

新規にこのvaultを導入する手順は、末尾の「セットアップ手順」を参照。日々の操作手順は`.claude/CLAUDE.md`の「コマンド」セクションと各スキルの`.claude/skills/<name>/SKILL.md`を参照。

## ディレクトリ構成

```
vault/
├── .claude/
│   └── CLAUDE.md          # Claude Code向け運用ルール（正典）
├── README.md              # このファイル
├── Inbox.base             # Obsidian Basesのビュー定義（6本共通）
├── Review.base
├── タスク.base
├── プロジェクト.base
├── 議事録.base
├── ノウハウ.base
├── Inbox/                 # 人間が書き込む唯一のゾーン（1件1ノート）
├── Review/                # AIの確認待ちゾーン（`## 要判断`欄に回答）
├── Today.md               # ピン留め単一ファイル（ブリーフィング＋メモ）
└── Cabinet/               # Claude Code専管ゾーン（人間は直接編集しない）
    ├── Diary/             # 過去のTodayの日次履歴
    ├── Notes/             # task/project/meeting/know-howをフラット格納
    ├── Documents/         # 資料保管庫。`[[ファイル名.pptx]]`でリンク
    ├── Assets/            # 添付画像
    ├── Templates/         # テンプレート
    └── MEMORY.md          # 長期記憶ファイル（詳細は後述）
```

## 役割分担

秘書業務を7機能（捕捉・判断・構造化・追跡・準備・報告・締め）に分解し、人間とClaude Codeの担当を固定する。

- **人間がやること**: 生の情報を`Inbox/`に書き留める、または`intake`スキルで直接渡す。AIが確信を持てない判断（分類不明・新規プロジェクト起票の可否等）に答える。答え方は`Today.md`の`## メモ`欄への自由記述、または`Review/`配下のノートの`## 要判断`欄への記入の2通り。日常的には`Today.md`と6本の`.base`を読み、Claude Codeを起動する（`/today`を1日の最初に1回）。
- **Claude Codeがやること**: 構造化・追跡・準備・報告・締めの全て。`Inbox/`の仕分け、`Cabinet/Notes/`への構造化、期限・進捗の追跡、会議前の準備、`Today.md`への報告、クリアデスクの実行。加えて、`context`が自動設定できなかったノート・カレンダーから無くなった議事録ノートの削除候補の検出、Reviewノートの回答確認と正式ノートへの変換も担う。

人間がObsidianのファイルエクスプローラーを操作して`Cabinet/`配下を直接編集・整理することは想定しない。

## コマンドとスキルの使い分け

`.claude/commands/`（単発コマンド）・`.claude/skills/`（スキル）はどちらも自然言語トリガーで呼び出せる（`description`により自動登録されるため）。両者の違いは呼び出し可否ではなく、手順の複雑さと誤操作リスク。

- **スキル**（`today`・`intake`・`setup`）: 複数手順・分岐があり、誤操作防止ガード（既存ファイルの上書き防止等）を要する操作。`.claude/skills/<name>/SKILL.md`に手順を定義する。
  - `today`: 開始・更新・締めの3モードを持つ。人間は1日の最初に`/today`を1回起動すればよく、以後は更新モードが`/loop`から数十分間隔で自動的に繰り返し呼ばれ、Inbox仕分け・Reviewノートの回答確認・カレンダー確認・期限確認を継続的に行う
  - `intake`: 会話に貼り付けられたメール・チャット本文からタスク候補を抽出しノート化する（貼り付けモードのみ。メールを自動走査するスキャンモードは持たない）
  - `setup`: 新規プロジェクトを起票する（`Cabinet/Notes/`にフラットな`project.md`ノートを1つ作成する。専用サブフォルダは作らない）
- **コマンド**: 単発・低リスクな操作（現時点では該当ファイル無し。`.claude/commands/`は存在しない）。

Downloadsフォルダの資料を`Cabinet/Documents/`へ入れる作業は、その都度の自然言語指示で行う（専用スキルは持たない）。

新しい操作を追加する際もこの基準で分類する。

## Baseの役割

Base（構造化フィルタ）は`Inbox.base`・`Review.base`・`タスク.base`・`プロジェクト.base`・`議事録.base`・`ノウハウ.base`の6本。

| 対象 | 答える問い | 使う場面 |
|---|---|---|
| Inbox（1ビュー） | まだ仕分けられていない書き留めはどれか | `Inbox/`フォルダを直接開く代わりに使う。通常は`today`スキルが自動で片付けるため、人間が能動的に見る必要はない |
| Review（1ビュー） | 人間の回答待ちの成果物はどれか | `## 要判断`欄に回答を書き込む対象を確認する時。通常は`today`スキルが分類不能・強制変換のタイミングで作成し、回答済みを検出して片付ける |
| タスク（7ビュー） | 今、何をすべきか | 「今日・今週やることを確認したい」「特定のプロジェクトの残作業だけ見たい」時に、TOPには出ていない他のビューに切り替えて使う |
| プロジェクト（4ビュー、うち2つは埋め込み専用） | 今動いているプロジェクトはどれか、状況は | 新しいプロジェクトを始める前に「今どれだけプロジェクトを抱えているか」を確認したい時。継続業務（旧area相当）は`due`を空欄にして表現する |
| 議事録（3ビュー） | どの議事録が未整理か、プロジェクト別にどう分布しているか | `context`設定漏れの検出、プロジェクト単位での俯瞰に使う |
| ノウハウ（2ビュー） | どのノウハウがどのプロジェクトに紐づくか | プロジェクト単位でノウハウを俯瞰したい時 |

タスクの7ビューのうち「タスク一覧」「期限順」「コンテキスト別」「チェック日順」「期限切れ・本日期限」「本日チェック」は既定で完了(`4_done`)・中止(`5_cancelled`)を除外表示にする。完了・中止も含めて見たい時は「タスク：すべて（完了・中止含む）」ビューに切り替える。

- **タスク一覧**: status（todo/doing/pending）別にグルーピング。何が滞留しているか俯瞰する
- **期限順**: 期限が近い順に並べる。日々一番よく使うのはこれ
- **コンテキスト別**: `context`でグルーピング。特定のプロジェクトに取り組んでいる時、その残作業だけ見たい時
- **チェック日順**: `check`（再確認日）が近い順に並べる。保留中・返答待ちのタスクについて、そろそろ再確認すべきものを見る時
- **期限切れ・本日期限**: `due`が今日以前（期限切れを含む）のものだけに絞り込む
- **本日チェック**: `check`が今日以前のものだけに絞り込む
- **タスク：すべて（完了・中止含む）**: 完了・中止を含む全件をstatus別にグルーピングして見る

プロジェクトの4ビューは「プロジェクト一覧」（完了除外、status別グルーピング）・「プロジェクト：すべて（完了含む）」・「関連タスク」・「関連議事録」。後2つは`file.hasLink(this.file)`でそのプロジェクトへの`context`リンクを持つノートだけに絞り込む埋め込み専用ビュー。単独では使わず、`Cabinet/Templates/project.md`の「進捗」節に`![[プロジェクト.base#関連タスク]]`・`![[プロジェクト.base#関連議事録]]`として埋め込んで使う。

議事録の3ビューは「全議事録一覧」（date降順）・「コンテキスト未設定」（`context`が空のものだけに絞り込み、割り振り漏れ・削除候補の検出に使う）・「コンテキスト別」（`context`でグルーピング）。

ノウハウの2ビューは「全ノウハウ一覧」（date降順）・「コンテキスト別」（`context`でグルーピング）。

Inboxの1ビューは「未処理Inbox一覧」（`file.folder == "Inbox"`で絞り込み、作成日時の降順）。`Inbox/`のノートは`type`を持たない一時状態のため、この1ビューだけを持つ。

Reviewの1ビューは「確認待ちReview一覧」（`file.folder == "Review"`で絞り込み、作成日時の降順）。`Review/`のノートも`type`を持たない一時状態のため、この1ビューだけを持つ。

`Today.md`の`## メモ`欄・`Cabinet/Diary/`の過去記録はBase化しない。`type`を持たず状態・期限による絞り込みの対象にならないため。探す時は全文検索（`Ctrl+Shift+F`）を使う。

## プロパティの使い方

### 命名規則

プロパティ名は英語・小文字・単語1つで統一している（`type` / `status` / `due` / `context` / `date` / `check` / `source`）。

新規プロパティを追加する際は、**テンプレート（`Cabinet/Templates/*.md`）・対応する`.base`ファイル・このREADMEの表**の3点を同時に更新すること。

### 型と値の統一表

| プロパティ | 型 | 許容値 | 用途 |
|---|---|---|---|
| `type` | 文字列（スカラー） | `task` / `project` / `meeting` / `know-how` | どのBaseに集計されるかを決める振り分けキー |
| `status` | 文字列（スカラー） | task: `1_todo` / `2_doing` / `3_pending` / `4_done` / `5_cancelled`。project: `1_active` / `2_done` | 進捗状態 |
| `due` | 日付文字列 `YYYY-MM-DD` | - | 期限。task・projectに存在する。projectで空欄なら旧area相当（終わりの無い継続業務） |
| `check` | 日付文字列 `YYYY-MM-DD` | - | 再確認日。taskのみ |
| `date` | 日付文字列 `YYYY-MM-DD` | - | ノート作成日。task・meeting・know-how、および`Inbox/`・`Review/`・`Cabinet/Diary/`のノートに存在し、テンプレートの`{{date}}`で自動入力される |
| `context` | 文字列（wikilink形式） | - | 紐づくプロジェクトへのリンク。全typeに共通の任意プロパティ。**唯一のリンク運用ルールで、常に高々1件**。指定するとバックリンクと`タスク.base`「コンテキスト別」に自動集計される |
| `source` | 文字列（自由記述） | 例: `intake` / `closing` | Reviewノートの発生元。`Review/`のノートのみに存在する |

`meeting`型はこれに加えて`calendar_event_id`／`calendar_series_id`（カレンダー連携用の識別子。`today`スキルが議事録ノートの重複生成防止と定例会議の引き継ぎに使う）を持つ。

`tags`・`goal`・`topic`は上記4 typeのプロパティとしては存在しない（廃止済み）。横断的な分類・検索は全文検索（`Ctrl+Shift+F`）に任せる。

議事録の出席者は本文の`## 出席者`見出しに書く。

### Baseごとの使い分け表

`●` = テンプレートに初期値がある必須プロパティ。`○` = テンプレートでは空欄の任意プロパティ。空欄 = そのtypeにはプロパティ自体が無い。

| プロパティ | task | project | meeting | know-how | Inbox | Review | Diary |
|---|---|---|---|---|---|---|---|
| `type` | ● | ● | ● | ● | | | |
| `status` | ● | ● | | | | | |
| `due` | ○ | ○ | | | | | |
| `check` | ○ | | | | | | |
| `date` | ● | | ● | ● | ● | ● | ● |
| `context` | ○ | ○ | ○ | ○ | | | |

`Inbox/`のノート（分類前の一時状態）と`Cabinet/Diary/`のノート（締め処理でリネームされた過去の`Today.md`）は`type`を持たず、`date`のみを持つ。`Review/`のノート（確認待ちの一時状態）も同様に`type`を持たないが、`date`に加えて`source`を持つ（上の表には含めない）。

### 運用フロー

- task・project・know-howの新規ノートはClaude Code（`today`スキルのInbox仕分け・`intake`・`setup`）が`Cabinet/Templates/*.md`を元に作成するのを正の経路とする。人間はテンプレート挿入で`Inbox/`に1件ノートを作るところまでを担う
- `Today.md`・議事録ノートは`today`スキル（`.claude/skills/today/SKILL.md`）を正の作成経路とする（`context`自動設定・日次git branchの作成のため）
- Reviewノートは`today`スキルが分類不能・強制変換のタイミングで作成し、人間が`## 要判断`欄に回答した後、次回の更新モードが正式ノート（`Cabinet/Notes/`）に変換して削除する（詳細は後述の「Reviewゾーンの運用」）
- `context`のようにノートを参照する値は手入力せず、プロパティパネルまたは`[[`の入力補完から既存ノートを検索して選ぶ
- `status`/`check`はObsidian上で直接書き換えず、Claude Codeへの自然言語指示（「Aタスクをdoingにして」等）を正の更新経路とする

## 更新履歴セクションの運用

`task`・`project`・`know-how`型のノートは、本文末尾に`## 更新履歴`セクションを持つ。ノート作成時に`- {{date}}: 作成`で初期化され、Claude Codeがそのノートの状態・内容を変更するたびに`- {{date}}: <変更内容>`を追記する。

frontmatterの`date`（作成日）だけでは事後の更新を日付でたどれないため、更新の記録は本文側のこのセクションで管理する。`meeting`型と`Inbox/`・`Review/`・`Cabinet/Diary/`のノートはこのセクションを持たない。

## MEMORY.mdの運用

`Cabinet/MEMORY.md`は`know-how`型（手順・ノウハウ）とは役割を分ける。「どうやるか」は`know-how`、「今何が前提として動いているか」は`MEMORY.md`が担う。

開始処理はこのファイルを読み込み、ブリーフィング作成の前提知識に使う。人間が直接編集することは想定しない。

## Reviewゾーンの運用

`Review/`は、AIが分類・判断に確信を持てない成果物を定型フォーマット（`## サマリー`／`## 要判断`／`## 本文`／`## 秘書メモ`）で確認待ちに置くゾーン。以下の2ケースでのみ使う。

- `intake`スキルで`type`・`context`の判定に確信が持てない場合
- 締め処理で`Inbox/`の未処理項目を強制変換する場合

人間は`## 要判断`欄の`- 回答: `行（コロンの右）に回答を書き込む。この行が回答済みかどうかの判定マーカーになる。次回の`today`スキルの更新モードが回答済みのReviewノートを検出し、正式なノート（`Cabinet/Notes/`）に変換してReviewノートを削除する。

通常の`update.md`によるInbox仕分けが「曖昧なため保留」するケースは対象外で、従来通り`Inbox/`に残る。

## リンクの運用ルール

リンクの役割を`context`1つに絞る。**`context` = このノートがどのプロジェクトに属するかを表す、常に高々1件のリンク。これが唯一の必須ルール。**

- task / meeting / know-how を作ったら、関係するプロジェクトがあれば`context`に1つリンクする
- それ以外の任意のリンク（`[[...]]`）は書きたい時に自由に書いてよく、必須ではない
- 何かを探す時はリンクを辿るのではなく、全文検索を使う

## Git運用: 日次ブランチ

Claude Codeは、ノートを新規作成・編集するBash/Write/Edit操作を行う前に、必ず今日の日次ブランチ（`daily/YYYY-MM-DD`）にいることを確認する。無ければ`main`から`git checkout -b daily/<今日の日付>`で作成する。既に存在すればチェックアウトするだけでよい。

日中はコミットしない。`today`スキルの締め処理が最後に今日の変更をひとつのコミットにまとめ、`main`へfast-forwardマージし、`git push`する。この運用のため、日中にvaultへ手動でコミットする操作（Obsidian Git等）は行わない。

## 既知の制約

- `context` プロパティ（wikilink）での `groupBy` は、Obsidian側の実装により見え方が変わる可能性がある。実際に開いて意図通りグルーピングされるか確認すること
- カレンダー連携（Google Calendar・Outlook）は実行環境ごとに利用可能なMCPツールが異なる。両方使える環境ではマージ、片方のみの環境ではそちらだけを使う。そのため、同じvaultでも環境によって`today`スキルが拾える会議候補の数が変わりうる
- `プロジェクト.base`の「プロジェクト一覧」「プロジェクト：すべて（完了含む）」テーブル自体には、各プロジェクトのタスク件数を列として出すrollup機能は無い
- 「関連タスク」「関連議事録」ビューはいずれもプロジェクトノートに埋め込んで使うそのプロジェクト単体の集計だが、出せる粒度が異なる

  | ビュー | `groupBy` | `summaries: file.name: Count`の意味 | 出せる集計 |
  |---|---|---|---|
  | 関連タスク | `status` | statusグループごとの件数 | 完了・未完了をstatusグループ単位で分けて確認できる |
  | 関連議事録 | なし | 紐づく議事録の単純合計件数 | `meeting`型に`status`プロパティが無いため、status別の件数は出せない |

- 複数プロジェクトを横並びで比較する集計表は無い
- `Today.md`は`today`スキルの開始モードだけが作成する。人間がObsidian側で先に`Today.md`を手で作ると、開始モードが「今日は既に始まっている」と誤判定して更新モードに入る
- `today`スキルの更新ループ（`/loop`）はセッションが生きている間だけ動く。PCを閉じる・セッションが切れると止まるため、翌日は人間が`/today`を1回起動して開始し直す
- `today`スキルの締め手順の日次ブランチマージは常にfast-forwardを前提にしている。`main`へ直接コミットする運用と併用すると、fast-forwardできず手動対応が必要になる場合がある
- Reviewノートには回答期限・自動失効の仕組みは無い。未回答のまま放置すると`Review.base`に蓄積し続けるため、定期的に`## 要判断`欄への回答を行う

## セットアップ手順

このvaultを新規に導入する手順。

### 前提

- Obsidian **1.11 以降**を使う。Basesがコア機能として使えるため。
- `today`スキルの締め手順（`.claude/skills/today/closing.md`）が日次ブランチを`main`へマージ後に`git push origin main`するため、リモートリポジトリ（`origin`）を設定しておく。設定しない場合は `git push`の手順だけ失敗する（マージ自体は成功する）。日次ブランチ運用の詳細は前述の「Git運用: 日次ブランチ」を参照。

### OneDrive環境での注意点

このvaultをOneDrive配下に置く場合、以下に注意する。

- **OneDriveの「ファイルオンデマンド」を無効化し、vaultフォルダを「常にこのデバイスに保持する」に設定する**: クラウードのみでローカルに実体が無い状態だと、Obsidianの全文検索やClaude Codeからのファイル読み書きが失敗・遅延する
- **`.git`フォルダをOneDrive外へ逃がす**: OneDriveの「フォルダーの選択」機能はトップレベルフォルダ単位でしか同期除外できず、`.git`のような特定のサブフォルダだけを除外することはできない。2026年8月に管理者向けの除外機能が追加されたが、個人アカウントでは使えないことが多い。放置すると同期処理と`git`のファイルロックが競合しリポジトリが破損するリスクがあるため、`git`の`--separate-git-dir`機能で`.git`の実体をOneDrive外へ移す。
  - [ ] OneDrive外の場所（例: `C:\Users\<ユーザー名>\git-data\obsidian.git`）を用意する
  - [ ] vaultルートで `git init --separate-git-dir=C:\Users\<ユーザー名>\git-data\obsidian.git` を実行する。既存リポジトリに対しても安全に適用できる。実行すると`.git`の中身がそのパスへ移動する。vaultルートには移動先を指す`.git`ポインタファイル1つだけが残る。
  - [ ] `git status`を実行し、リポジトリが正常に認識されることを確認する
- **複数端末で同時にvaultを開かない**: 同一vaultを別PC・別デバイスで同時に開くと、OneDriveの同期タイミングのズレでノートの重複ファイル（`ファイル名-PC名.md`等）や`.git`の競合が起きる。編集は1台に絞るか、片方を閉じてから他方を開く

### Obsidianの基本設定

**エディタ**
- デフォルトビューを `リーディングビュー` にする
- 読みやすい行の長さを `off` にする
- 行番号の表示を `on` にする
- ノートにMermaid図を表示を `on` にする
- インタインタイトルを `off` にする

**ファイルとリンク**
- 内部リンクを毎回更新するを `on` にする
- すべてのファイル拡張子を認識を `on` にする
- 新規ノートの作成場所・新規添付ファイルの保存先・起動時に開くファイルは、後述の「セットアップ手順」内で設定する

**外観**
- 好みのテーマを設定する（`Typora-Vue`がすっきりしつつ色味がよい）

### 1. Gitリポジトリを初期化する

`today`スキルの締め手順が日次ブランチのマージ・pushを行うため、他の手順より先に済ませておく。

- [ ] vaultルートで `git init` を実行する
- [ ] デフォルトブランチ名を `main` にする（`git init -b main` を使うか、初期化後に `git branch -m main` でリネームする）
- [ ] `.gitignore` を作成し、以下を除外する（ローカル環境依存でノイズになるため）:
  ```
  .obsidian/workspace.json
  .obsidian/workspace-mobile.json
  .trash/
  ```
- [ ] 初回コミットを作成する（`git add .` → `git commit -m "Initial commit"`）
- [ ] （任意）リモートリポジトリ（GitHub等）を用意し、`git remote add origin <URL>` で紐付ける
- [ ] （任意）`git push -u origin main` で初回pushする。リモートを設定しない場合はスキップしてよい（ローカルのみで運用でき、`today`スキルの締め手順はマージまで成功しpush手順のみ失敗する）

### 2. フォルダを作成する

vaultルート直下に`Inbox/`・`Review/`・`Cabinet/`を作り、`Cabinet/`配下に`Diary/`・`Notes/`・`Documents/`・`Assets/`・`Templates/`を作成する（上記「ディレクトリ構成」のツリー図を参照）。

- [ ] `Cabinet/MEMORY.md`を作成する。初期内容は見出し`# MEMORY`のみでよい。以降は締め処理が「昇格判断」で追記する

### 3. `.base` ファイルをvaultルート直下に配置する

- [ ] `Inbox.base`・`Review.base`・`タスク.base`・`プロジェクト.base`・`議事録.base`・`ノウハウ.base`をルートディレクトリに配置する

### 4. `Cabinet/Templates` にテンプレートファイルを配置する

- [ ] `task.md` / `project.md` / `meeting.md` / `know-how.md` / `today.md` / `inbox.md` / `review.md` を `Cabinet/Templates/` にコピーする
- [ ] `設定 → コアプラグイン → テンプレート` を有効化し、テンプレートフォルダの場所を `Cabinet/Templates` に設定する
- [ ] `設定 → コアプラグイン → デイリーノート` を**無効化**する。`Today.md`（`today`スキルが管理）が同じ役割を担うため、コアプラグイン側が別途デイリーノートを作らないようにする
- [ ] `設定 → ファイルとリンク → 起動時に開くファイル` を `最後に開いたファイル` に設定する
- [ ] `設定 → ファイルとリンク → 新規ノートの作成場所` を `Inbox` に設定する
- [ ] `設定 → ファイルとリンク → 新規添付ファイルの保存先` を `Cabinet/Assets`に設定する
- [ ] `Today.md`をブックマーク（ピン留め）し、いつでもすぐ開けるようにする

### 5. ショートカットキーを割り当てる

- [ ] `設定 → ホットキー` で「テンプレート: テンプレートを挿入」に任意のキー（例: `Ctrl+Shift+N`）を割り当てる
- [ ] `設定 → ホットキー` で「ノート: 新規ノートを作成」に任意のキー（例: `Ctrl+N`）を割り当てる（`Inbox/`への書き留めに使う）
- [ ] `設定 → ホットキー` で「ペイン: 右に分割」に任意のキー（例: `Ctrl+R`）を割り当てる
- [ ] `設定 → ホットキー` で「右のサイドバーを開閉」に任意のキー（例: `Ctrl+,`）を割り当てる
- [ ] `設定 → ホットキー` で「左のサイドバーを開閉」に任意のキー（例: `Ctrl+.`）を割り当てる

### 6. Claude Codeコマンドを配置する

- [ ] `CLAUDE.md`を`.claude/`配下に配置する
- [ ] `.claude/skills/today/`（`SKILL.md`・`opening.md`・`update.md`・`closing.md`）／`intake/SKILL.md`／`setup/SKILL.md` を配置する
- [ ] （任意）Google CalendarまたはOutlookのMCP連携を設定する。設定しない場合、`today`スキルの開始時のカレンダー連携部分は自動でスキップされる

### 7. 運用を開始する

- [ ] 1日の最初に`/today`を1回起動する。以後は`/loop`によって更新モードが自動で繰り返され、締め処理まで人間の起動は不要（締め処理でループは停止するため、翌日また`/today`を起動する）

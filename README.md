# Obsidian vault 使い方

タスク管理・メモ・議事録など業務全体を1つのvaultで管理するための構成。`type`
プロパティでBasesを絞り込むため、ノートをどのフォルダに置いても正しく集計
される。Obsidianコア機能（Bases・全文検索・テンプレート）に加え、
日々の操作と検出をClaude Codeに委譲する（詳細は`CLAUDE.md`を参照）。
コミュニティプラグインは使わない。

新規にこのvaultを導入する手順は`SETUP.md`を参照。

## 役割分担

- **Obsidian（見る場所）**: Bases・デイリーノート・テンプレートで「今の
  状態」を眺める。
- **Claude Code（操作・検出する場所）**: デイリーノート生成・議事録作成・
  ステータス更新・Web取り込みといった日々の操作と、放置タスク・プロジェクト未設定
  議事録の検出を担当する。

## Baseの役割

Base（構造化フィルタ）は`タスク.base`と`プロジェクト.base`の2本。タスクとプロジェクトだけが「状態・期限
で絞り込んで一覧する」価値が高いため、この2種類だけをBase化している。

| 対象 | 答える問い | 使う場面 |
|---|---|---|
| タスク（7ビュー） | 今、何をすべきか | 「今日・今週やることを確認したい」「特定のプロジェクトの残作業だけ見たい」時に、TOPには出ていない他のビューに切り替えて使う |
| プロジェクト（2ビュー） | 今動いているプロジェクトはどれか、状況は | 新しいプロジェクトを始める前に「今どれだけプロジェクトを抱えているか」を確認したい時。継続業務（旧area相当）は`due`を空欄にして表現する |

タスクの7ビューのうち「タスク一覧」「期限順」「コンテキスト別」
「チェック日順」「期限切れ・本日期限」「本日チェック」は既定で完了(`3_done`)
を除外表示にする。完了も含めて見たい時は「タスク：すべて（完了含む）」
ビューに切り替える。

- **タスク一覧**: status（todo/doing）別にグルーピング。何が滞留しているか俯瞰する
- **期限順**: 期限が近い順に並べる。日々一番よく使うのはこれ
- **コンテキスト別**: `context`でグルーピング。特定のプロジェクトに取り組んでいる時、その残作業だけ見たい時
- **チェック日順**: `check`（再確認日）が近い順に並べる。保留中・返答待ちのタスクについて、そろそろ再確認すべきものを見る時
- **期限切れ・本日期限**: `due`が今日以前（期限切れを含む）のものだけに絞り込む
- **本日チェック**: `check`が今日以前のものだけに絞り込む
- **タスク：すべて（完了含む）**: 完了を含む全件をstatus別にグルーピングして見る

プロジェクトの2ビューは「プロジェクト一覧」（完了除外、status別グルーピング）と「プロジェクト：すべて
（完了含む）」。

**議事録・メモ・ノウハウはBase化しない。** これらは状態・期限で絞り込む必要
が薄く、「特定の1件を思い出して辿る」用途が中心のため、全文検索
（`Ctrl+Shift+F`）・`/find`コマンド・プロジェクトノートの自動バックリンク（`context`
を設定した議事録・ノウハウはプロジェクトノート側から辿れる）で探す。

## プロパティの使い方

### 命名規則

プロパティ名は英語・小文字・単語1つで統一している（`type` / `status` /
`due` / `context` / `date` / `check`）。

新規プロパティを追加する際は、**テンプレート（`92_Template/*.md`）・対応する
`.base`ファイル・このREADMEの表**の3点を同時に更新すること。

### 型と値の統一表

| プロパティ | 型 | 許容値 | 用途 |
|---|---|---|---|
| `type` | 文字列（スカラー） | `task` / `project` / `meeting` / `know-how` | どのBaseに集計されるかを決める振り分けキー |
| `status` | 文字列（スカラー） | task: `1_todo` / `2_doing` / `3_done`。project: `1_active` / `2_done` | 進捗状態 |
| `due` | 日付文字列 `YYYY-MM-DD` | - | 期限。task・projectに存在する。projectで空欄なら旧area相当（終わりの無い継続業務） |
| `check` | 日付文字列 `YYYY-MM-DD` | - | 再確認日。taskのみ |
| `date` | 日付文字列 `YYYY-MM-DD` | - | ノート作成日。task・meeting・know-how・memoに存在し、テンプレートの`{{date}}`で自動入力される |
| `context` | 文字列（wikilink形式） | - | 紐づくプロジェクトへのリンク。全typeに共通の任意プロパティ。**唯一のリンク運用ルールで、常に高々1件**。指定するとバックリンクと`タスク.base`「コンテキスト別」に自動集計される |

`tags`・`goal`・`topic`は上記5 typeのプロパティとしては存在しない
（廃止済み）。横断的な分類・検索は全文検索（`Ctrl+Shift+F`）または`/find`
コマンドに任せる。デイリーノートのみ、typeスキーマとは無関係な固定マーカー
として`tags: [daily]`を例外的に持つ（Basesはこれを参照しない）。

議事録の出席者は本文の`## 出席者`見出しに書く。

### Baseごとの使い分け表

`●` = テンプレートに初期値がある必須プロパティ。`○` = テンプレートでは空欄の任意プロパティ。空欄 = そのtypeにはプロパティ自体が無い。

| プロパティ | task | project | meeting | know-how | memo |
|---|---|---|---|---|---|
| `type` | ● | ● | ● | ● | |
| `status` | ● | ● | | | |
| `due` | ○ | ○ | | | |
| `check` | ○ | | | | |
| `date` | ● | | ● | ● | ● |
| `context` | ○ | ○ | ○ | ○ | ○ |

### 運用フロー

- task・project・know-how・memoの新規ノートはテンプレート挿入
  （`92_Template/*.md`）から作成する。議事録は`/meeting`、デイリーノートは
  `/daily`を正の作成経路とする（`context`自動設定・日次git branchの作成の
  ため）
- `context`のようにノートを参照する値は手入力せず、プロパティパネルまたは
  `[[`の入力補完から既存ノートを検索して選ぶ
- `status`/`check`はObsidian上で直接書き換えず、Claude Codeへの
  自然言語指示（「Aタスクをdoingにして」等）を正の更新経路とする

## リンクの運用ルール

リンクの役割を`context`1つに絞る。**`context` = このノートがどのプロジェクトに
属するかを表す、常に高々1件のリンク。これが唯一の必須ルール。**

- task / meeting / know-how を作ったら、関係するプロジェクトがあれば`context`に
  1つリンクする
- それ以外の任意のリンク（`[[...]]`）は書きたい時に自由に書いてよく、
  必須ではない
- 何かを探す時はリンクを辿るのではなく、全文検索または`/find`を使う

## 業務での使い方（操作手順）

- **1日の作業はデイリーノートで回す**: Claude Codeで`/daily`を実行する
  （無ければ生成、あれば開く）。今日の日次git branch（`daily/YYYY-MM-DD`）
  も自動的に作成・チェックアウトされる。カレンダー連携があれば当日の
  会議候補から議事録の下書きも事前生成される
- **メモを気軽に追加**: 日次ノートの`## メモ`欄に直接書く（デフォルトの
  書き先）。後から「これは単独ノートとして残したい・後で検索やリンクの
  対象にしたい」と判断したものだけ、`Ctrl+N`→テンプレート挿入で`memo`を
  選び`10_Inbox`に切り出す（昇格操作）。この判断は`/wrapup`実行時の
  棚卸でも提案される
- **タスクを1件追加**: `Ctrl+N` → テンプレート挿入で`task`。作成日は自動
  入力される
- **議事録を作る**: Claude Codeで`/meeting <案件名>`を実行する。`context`
  は自動設定され、同じ案件の議事録が既に2件以上あれば定例用の固定
  テンプレートが使われる。本文中の未チェックのアクションアイテムは、
  ノート確定後にClaude Codeが自動でタスク化する
- **新しいプロジェクトが立ち上がる**: `Ctrl+N` → テンプレート挿入で`project`。
  終わりの無い継続業務（旧area相当）は`due`を空欄のままにする
- **状況を確認する**: Claude Codeで`/audit`を実行すると、放置タスク・
  プロジェクト未設定の議事録・タスク化されていないアクションアイテムが一覧で
  出てくる（読み取り専用）
- **タスクを棚卸する**: Claude Codeで`/task`を実行すると、vault全体の
  放置タスク・未タスク化のアクションアイテムを対話的に確認しながら、
  更新・削除・追加まで行える（`/audit`と違い、実際に手を入れられる）
- **1日を締める**: 1日の終わりにClaude Codeで`/wrapup`を実行する。今日
  作成・編集したノートの`context`補完・議事録アクションアイテムのタスク化・
  Teams/Copilot議事録の転記（連携があれば）はその場で自動修正され、
  未完了の今日のTodo・メモ欄からの昇格候補・明日の準備がまとめて
  報告される。`30_Work`・`40_Knowledge`直下に置きっぱ
  なしのノートもプロジェクト・カテゴリのフォルダへ自動整理される。最後に今日の
  変更をひとつのコミットにまとめ、日次ブランチを`main`へマージして
  `git push`する
- **Webページを取り込む**: Claude Codeで`/clip <URL>`を実行すると、要約
  された状態でメモノートが`10_Inbox`に作られる
- **何かを探す**: 全文検索（`Ctrl+Shift+F`）または`/find <キーワード>`
- **ノウハウ・手順を記録する**: `Ctrl+N` → テンプレート挿入で`know-how`

## 既知の制約

- `context` プロパティ（wikilink）での `groupBy` は、Obsidian側の実装により
  見え方が変わる可能性がある。実際に開いて意図通りグルーピングされるか
  確認すること
- カレンダー連携（Google Calendar・Outlook）は実行環境ごとに利用可能な
  MCPツールが異なる。両方使える環境ではマージ、片方のみの環境ではそちら
  だけを使うため、同じvaultでも環境によって`/daily`が拾える会議候補の数が
  変わりうる
- プロジェクト/エリアごとの完了・未完了「件数」を数値で出す機能（rollup）
  は組み込んでいない
- Obsidianの「起動時に開くファイル」設定により、その日最初にObsidianを
  開いた時点でデイリーノートがコア機能側で自動生成される。この時点では
  Claude Codeを経由していないため、日次ブランチが未作成のまま`main`上に
  未コミットの変更として残る。実害は無い（`/daily`等を最初に実行した瞬間
  に日次ブランチへ持ち越される）が、その日Claude Codeを一度も使わなければ
  翌日以降に持ち越される
- `/wrapup`の日次ブランチマージは常にfast-forwardを前提にしている。`main`
  へ直接コミットする運用と併用すると、fast-forwardできず手動対応が必要に
  なる場合がある

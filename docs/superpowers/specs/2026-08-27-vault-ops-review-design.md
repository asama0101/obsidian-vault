# Obsidian Vault 運用体制 敵対レビュー＆改善 設計書

- 日付: 2026-08-27
- ブランチ: `feature/vault-system-review`
- 起点: `92_Template/daily.md`確認完了、他コマンド/スキル/テンプレート/Basesは未確認

## 背景・現状

初回調査（Exploreエージェント）で判明した事実:

- コマンド8種（`daily`/`meeting`/`audit`/`task`/`clip`/`find`/`status`/`wrapup`）のうちスキル化済みは`daily`のみ。他7種は`.claude/commands/*.md`の素のスラッシュコマンドで、自然言語トリガー（例:「今日のノート開いて」）を持たない。
- `10_Inbox/テストタスク①②③.md`の本文コメントに廃止済みコマンド名`/review`が残存（正しくは`/audit`）。
- `.claude/commands/task.md`は対象を`30_Work/`配下に限定するが、`10_Inbox`にも`type: task`ノートが実在し、`/audit`（vault全体を横断と明記）とスコープ定義が食い違う。
- `20_Diary`が空。`daily`→`wrapup`の一連フローが実データで一度も検証されていない。
- `プロジェクト.base`・`タスク.base`のみ存在し、`meeting`・`know-how`にはBaseビューが無い。
- `project.md`テンプレートの`## 進捗`見出しが既存プロジェクトノート全件で未反映（`/wrapup`/`/status`未実行のため、不具合ではなく未検証状態）。
- git履歴からこの運用体制はごく最近整備されたばかりで、ドキュメントと実装の同期作業が継続中。

## 目的

以下4観点＋その他の気づきを敵対的にレビューし、実データ（サンプル）で動作させて人が評価できる状態まで仕上げる。

1. 業務遂行可能か（欠落フロー・矛盾の有無）
2. 管理/棚卸しやすいか（Bases・コマンドで状態を把握できるか）
3. Claude Codeのスキルで省人化できるか（コマンド→スキル昇格の要否）
4. 陳腐化しないか（データが増えた後も破綻しない設計か）

## アーキテクチャ

### レビュー体制: 4視点並列レビュー→集約→修正→再レビューのループ

```
[ラウンドN開始]
  Main: 対象ファイル一覧を4エージェントへ並列委任
    - reviewer-se-user      現場SE利用者視点
    - reviewer-maintainer   保守者視点（整合性・矛盾）
    - reviewer-staleness    陳腐化チェッカー視点
    - reviewer-skill-design スキル設計者視点
  Main: 4エージェントの所見をtool結果として受領（file:line形式で簡潔に）
  Main: 重複排除・優先度付け（Critical/Major/Minor）
  Main: 修正を委任
    - ドキュメント/コマンド定義の文言修正 → doc-updater
    - 機械的な誤記修正 → trivial-executor
    - コマンド→スキル昇格 → skill-creator スキル
    - Base定義（.base JSON）修正 → Main直接（exact-editに該当する場合）
  Main: git status/diffで変更の実在を確認（サブエージェント報告を鵜呑みにしない）
[ラウンドN終了: Critical=0 か ラウンド数=3 で判定]
  Critical>0 かつ ラウンド<3 → 次ラウンドへ（新規コンテキストのエージェントで再レビュー）
  それ以外 → ループ終了
```

- 各ラウンドのレビューエージェントは**前ラウンドの所見を持たない新規コンテキスト**で起動する（自己承認・確証バイアスの排除）。
- 4エージェントは独立起動のため`Agent`ツールの並列呼び出し（1メッセージ内に複数tool_use）で実施する。
- 停止基準: 重大指摘ゼロ、上限3周（ユーザー承認済み）。3周到達時点でCriticalが残る場合はループを止め、残存事項をユーザーに報告して判断を仰ぐ。

### レビュー対象ファイル

| カテゴリ | パス |
|---|---|
| コマンド定義 | `.claude/commands/*.md`（7ファイル） |
| スキル | `.claude/skills/*/SKILL.md` |
| テンプレート | `92_Template/*.md`（7ファイル） |
| Bases | `*.base`（`タスク.base`/`プロジェクト.base`、meeting/know-how分の要否含む） |
| プロジェクト設定 | `.claude/CLAUDE.md` |
| 操作マニュアル | `00_README/*`（13ファイル） |
| 既存サンプルノート | `10_Inbox/*`（`/review`残存等の実データ側矛盾） |

### コマンド→スキル昇格の判断基準

以下いずれかに該当すればスキル化を検討する（該当しない単純コマンドは現状維持）:

- 自然言語での呼び出し需要が高い（例:「議事録作って」「棚卸しして」）
- 複数手順・分岐があり誤操作リスクがある（`wrapup`のような多段処理）
- 他スキル（`daily`）との一貫性上、同格の操作なのにスキル化されていないと不自然

`skill-creator`スキルを使って実際のスキルパッケージ化を行う。

### サンプルデータ

SEペルソナ（`00_README`の想定利用者像に準拠）で以下を作成し、`20_Diary`・`30_Work`配下に投入する。

- 直近1週間分（5〜7日）のデイリーノート（`20_Diary/`）: スケジュール・繰り返しタスク・今日のタスク・議事録・メモを埋めた実データ
- 進行中案件2〜3件（`30_Work/`配下、サブフォルダ運用）: project 1〜2件＋紐づくtask複数＋meeting複数（うち1件は3件目以降で`meeting-recurring.md`が選ばれることを検証）＋know-how 1件程度
- 上記を通じて`/daily`→`/task`→`/meeting`→`/wrapup`→`/status`の一連フローが実データで機能することを示す

既存の`10_Inbox`テストノート（`/review`残存分）はレビュー対象として修正 or 整理する（削除が必要な場合はユーザー確認を取る）。

## データフロー

1. Main: 調査結果（本設計の「背景・現状」）を各ラウンドの初期入力としてレビューエージェントに渡す（ラウンド2以降は直前ラウンドの修正差分も渡す）
2. レビューエージェント: 対象ファイルを読み、指摘を`file:line`＋重大度で返す
3. Main: 指摘を集約し修正委任
4. 修正エージェント: ファイルを編集し、変更点をMainへ報告
5. Main: `git status`/`git diff --stat`で実変更を確認
6. 次ラウンドへ

## エラーハンドリング・安全策

- 破壊的操作（ノート削除等）が必要な指摘が出た場合、Mainは実行せず方法を提示してユーザー承認を待つ（CLAUDE.md「削除制限」）。
- サブエージェントへの委任時は「安全装置ブロック時は即停止しBLOCKEDと報告」「同一ブランチへの複数Bash権限エージェント並行時はworktree破棄操作禁止」を委任プロンプトに明記する。
- 3周を超えてもCriticalが残る場合はループを打ち切り、ユーザーに残存事項を提示して指示を仰ぐ（無限ループ防止）。
- push前に必ずユーザーの最終承認を取る（CLAUDE.mdの確認必須操作）。

## 検証・完了条件

- 各ラウンド後、Critical指摘件数で継続/終了を判定
- サンプルデータ投入後、`/daily`・`/wrapup`等が実際に対象データに対して意図通り動くこと（可能な範囲でコマンド実行して確認、またはロジックを人手でトレース）
- 全修正完了後、ユーザーに成果物一覧（変更ファイル・新規スキル・サンプルデータ）を提示し評価を仰ぐ
- ユーザー承認後にコミット→push

## スコープ外

- Obsidianプラグインの追加・設定変更
- Bases機能自体の仕様変更（Obsidian側の制約に従う）
- 過去分（1週間より前）のデイリーノート遡及作成

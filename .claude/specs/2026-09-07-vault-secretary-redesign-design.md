# Obsidian秘書vault 再設計 設計書

作成日: 2026-09-07
対象: `/home/asama/obsidian-vault` 全体（フォルダ構成・ノートスキーマ・スキル群・閲覧面）
方針: 破壊的変更を許容する。既存データの移行は考慮しない。

## 1. 背景

現行vaultは一度も本番運用されていない。

- 実ノートは `20_Diary/2026-09-02.md` の1件のみ（35行）。内部リンク4本すべてが削除済みフォルダを指す。
- `Cabinet/Notes/` は空。`Today.md` は存在しない。`Cabinet/MEMORY.md` は見出しのみの2行。
- 一方で仕組み側は README 288行 + CLAUDE.md 143行 + テンプレート206行 + `.base` 284行 ＝ 約920行。
- 直近11コミットはすべてスキル・テンプレート・ドキュメントの改訂で、実ノートの追加は0件。

負荷の原因は機能不足ではなく、次の3点である。

1. **接点の分散**: 人間の書き込み口が `Inbox/`・`Today.md`の`## メモ`・`Review/`の`- 回答: `の3か所にあり、書くたびに「どこに書くか」の判断が発生する。
2. **全走査アーキテクチャ**: `type`/`status`/`due` がfrontmatterにしか無く索引が無いため、タスク抽出も会議照合も `Cabinet/Notes/` 全件読みになる（`update.md:33`, `opening.md:10,13`, `closing.md:16`）。これを `/loop` が30分間隔で1日約28回繰り返す。
3. **判断基準の不在**: 分類基準が `intake/SKILL.md:15` と `today/update.md:5-14` に分散し、前者は後者を参照しているが後者に実体が無い。基準が事実上どこにも存在しない。

## 2. 設計方針

**接点を1枚に、判断を1か所に、読み取りを定数に。**

- 人間が触れるのは `Today.md` だけ。
- 分類基準が書かれているのは `secretary` スキルだけ。
- ループがvaultを読む経路は索引スクリプトだけ。

機能は削らない。会議・タスク・プロジェクト・ノウハウの4機能すべてを維持し、削るのは機構（ゾーン数・テンプレート・状態遷移・判断ルールの数）である。

## 3. フォルダ構成

```
vault/
├── Today.md                    ← 人間との唯一の接点
├── Documents/                  ← 人間がドラッグ&ドロップで投入する資料
├── Cabinet/                    ← Claude Code専管ゾーン
│   ├── Notes/                  ← task/project/meeting/know-how をフラット格納
│   ├── Diary/                  ← 締めでリネーム移動された過去のToday
│   ├── Assets/                 ← Obsidianの添付ファイル自動振り分け先
│   ├── Templates/              ← 5本（today + 4type）
│   ├── Bases/                  ← .base 4本
│   └── MEMORY.md               ← 長期記憶
└── .claude/
    ├── CLAUDE.md
    ├── settings.local.json
    ├── specs/                  ← 本書。ドットフォルダなのでObsidianに表示されない
    ├── scripts/                ← index.py / new_note.py / close_day.sh
    ├── skills/secretary/SKILL.md
    └── commands/               ← today.md / intake.md / close.md
```

`Documents/` をvault直下に置く理由は、人間がドラッグ&ドロップで投入するゾーンであり、「人間は直接編集しない」と定義した `Cabinet/` の中にあるべきでないため。

`Cabinet/Bases/` に `.base` を落とす理由は、日常では見ず必要な時だけたどる棚であり、vault直下に並べる必要がないため。

`Assets/` は `Cabinet/` に残す。Obsidianの添付ファイル設定で自動振り分けされ、人間がフォルダを意識して操作する場面が無いため。

## 4. `Today.md` 仕様

vault直下に常に1つだけ存在する単一ファイル。人間とAIの唯一の接点。

```markdown
---
date: 2026-09-07
---
## 今日の予定
- 10:00-11:00 [[週次定例]]
（取得元: Google ✓ / Outlook 未接続）

## 今日のタスク
- [ ] [[見積書の作成]] 期限 今日
- [ ] [[環境構築]] 進行中

## 確認したいこと
- 「A社の件」はタスクとノウハウどちらですか？ →

## メモ
- B社に折返し電話 → [[B社への折返し]]
- 来週の資料まとめる
```

### 各セクションの編集権

| セクション | AI | 人間 | 更新モードの操作 |
|---|---|---|---|
| `## 今日の予定` | 書く | 読む | 全置換（毎回再生成） |
| `## 今日のタスク` | 書く | 読む・終わった行にチェックを入れる | チェック済み行を完了として処理した後、全置換（毎回再生成） |
| `## 確認したいこと` | 質問行を追加 | `→` の右に回答 | 回答済み行を処理して削除、新規質問を追加 |
| `## メモ` | リンク追記のみ | 自由記述 | 未処理行を処理し、行の後ろに ` → [[ノート名]]` を追記 |

- 処理済みのメモ行は削除しない。元の文言を残したままリンクを追記する。
- `## メモ` は締めで `Cabinet/Diary/` へ退避されるので蓄積しない。
- `## 確認したいこと` の回答マーカーは `→` の右に文字があるかで判定する。

### Today.md の行書式

更新モードは上2セクションを毎回全置換するため、書式を固定しないと出力が日々揺れる。次の形に統一する。

- `## 今日の予定`: `- HH:MM-HH:MM [[議事録ノート名]]`。終日予定は時刻を `終日` とする。セクション末尾に `（取得元: ...）` の1行を置く。チェックボックスは使わない。
- `## 今日のタスク`: `- [ ] [[タスクノート名]] <状態>`。`<状態>` は `期限 今日` / `期限超過 N日` / `進行中` のいずれか。

チェックボックスを持つのは `## 今日のタスク` だけとする。更新モードが両セクションを全置換するため、押しても読まれないチェックボックスは「押せるのに何も起きない」UIになる。タスク側はチェックを完了の合図として読み、状態をノート側の frontmatter（`status: 4_done` / `done`）に移すことで意味を与える。状態がノートにあるため全置換と冪等性は保たれる。予定側にはチェックの受け先が無いので素の箇条書きにする。
- `## 確認したいこと`: `- <質問>（N回目） →`。
- `## メモ`: 人間の自由記述。処理済み行は元の文言の後ろに ` → [[ノート名]]` を足す。`context` を新規に提案した場合は ` → [[ノート名]]（context: 提案値）` となる。

### 処理済みマーカーの判定規約

`## メモ` の行が処理済みかどうかは、**行内に `→ [[...]]` を含むかで判定する。行末では判定しない。** 第9章で `context` の新規提案を認めたことにより、処理済み行の行末が `（context: 提案値）` になりうるため。行末で判定すると、更新モードが30分ごとに同じ行を未処理と誤判定し、同名衝突で `new_note.py` が失敗する経路に毎回入るか、マーカーが多重に追記されて行が壊れる。

`- 前日の未処理:` で始まる繰越行（第7章の開始モードが書く行）は処理対象外とし、未処理件数にも数えない。AIが自分で書いた行であり、人間の依頼ではないため。

## 5. ノートスキーマ

`Cabinet/Notes/` にフラット格納。`type` で判別する。サブフォルダは作らない。

| type | frontmatter | 本文セクション |
|---|---|---|
| `task` | type, date, status, due, done, context | `## 完了条件` / `## 作業ログ` |
| `project` | type, date, status, due, context | `## 概要` / `## 現状と次の一手` / `## 経緯` / `## 関連` |
| `meeting` | type, date, status, context, calendar_event_id, calendar_series_id | `## 議題` / `## 資料` / `## メモ` / `## 決定事項` / `## アクション` |
| `know-how` | type, date, context | `## 状況` / `## 手順` / `## 注意点` |

### status の値域

- `task`: `1_todo` / `2_doing` / `3_pending` / `4_done` / `5_cancelled`
- `project`: `1_active` / `2_done`
- `meeting`: `1_予定` / `2_実施済` / `3_中止` / `4_不参加`

`meeting` の `status` は新設。現行は会議キャンセルを検出する手順（`update.md:29`）があるのに記録する場所が無かった。

`3_中止` は会議そのものが取り消された場合、`4_不参加` は会議は開催されたが自分が出席しなかった場合。後者は他の出席者の議事録を後から取り込む余地が残るため、区別する。

### 更新履歴の扱い

- `task` / `meeting` / `know-how` は `## 更新履歴` を持たない。
- `task` の完了日は frontmatter の `done` プロパティで持つ。
- `project` のみ `## 経緯` を持ち、**方針・判断の変化だけ**を記録する。status変更では書かない。

理由: 締め処理が1日分を1コミットにまとめるため git log から個別ノートの変更理由は復元できないが、機械的なstatus遷移は記録する情報量がほぼゼロであり、書き込み回数を倍にする価値がない。方針転換の理由だけは人間が読む価値があり、差分からは意図が読み取れない。

### テンプレート

`Cabinet/Templates/` に today / task / project / meeting / know-how の5本。type別の4本は最小骨とし、空欄の見出しを量産しない。必要になったセクションはAIがその都度追加する。`today.md` は第4章の4セクション構成の雛形。

`meeting` のみ5セクションになるのは `## 資料` を持つため（第8章の資料紐付けを参照）。

`project` の `## 関連` には `![[プロジェクト.base#関連ノート]]` を埋め込み、そのプロジェクトにリンクしているタスクと議事録を一覧する。第11章の埋め込み用ビューの受け先。

### ノート名の規約

`meeting` のノート名は `YYYY-MM-DD 会議名` とする。定例会議は毎回同じイベント名を持つため、日付を含めないと2回目の生成が同名衝突で失敗する。他の3種は件名をそのまま使う。

### 資料の紐付け

会議で参照する資料は `meeting` ノートの `## 資料` から**片方向にリンクする**。逆引きはObsidianのバックリンクで行う。

`Documents/` にはPDFやxlsxが入り、Obsidianのプロパティは `.md` にしか付かないため、資料側にメタデータを持たせる方式は採らない。

`## 資料` には2つの記法が混在する。

- カレンダー由来の外部資料: `- [見積書_A社](https://drive.google.com/...)`
- vault内の資料: `- [[見積書_A社.pdf]]`（人間がObsidian上で貼るか、`## メモ` で指示する）

## 6. 実行機構の割り当て

| 種別 | 対象 | 実装 |
|---|---|---|
| スクリプト | 機械的処理 | `.claude/scripts/` |
| スキル | 判断を伴う定型処理 | `.claude/skills/secretary/` |
| カスタムコマンド | 入口 | `.claude/commands/` |
| サブエージェント | 並列可能な読み取り | Explore（読み取り専用） |

### スクリプト

**`index.py`** — `Cabinet/Notes/` 配下の全 `.md` のfrontmatterを解析し、1行1ノートのTSVを標準出力に返す。

- 出力列: `path`, `type`, `status`, `due`, `done`, `context`, `date`, `title`, `mtime`, `calendar_event_id`, `calendar_series_id`（11列）
- `calendar_event_id` と `calendar_series_id` を含めるのは、会議ノートの照合をこの索引だけで完結させるため。これらが無いと、カレンダーのイベントと既存の議事録ノートを突き合わせる手段が個別Readしか残らず、定数コストの前提が崩れる
- `title` はファイル名から拡張子を除いたもの。frontmatterには持たない
- オプション: `--type`, `--status`, `--date`, `--updated-on` で絞り込む。`--type` と `--status` はカンマ区切りで複数値を受け付け、OR条件として扱う
- `--date` は frontmatter の `date` が完全一致する行だけを返す。会議の照合とキャンセル判定を当日分に限定するために要る。これが無いと `--type meeting` が過去の全議事録を返し、呼び出し回数が定数でも出力量がノート件数に比例して増える
- 複数のオプションを併用した場合はAND条件として扱う
- `--contexts` で既存の context 値を重複排除して一覧出力する
- 値が空のプロパティは空文字列として出力する。行数はノート数と常に一致する
- ループがvaultを読む唯一の経路。個別ノートのReadは、実際にそのノートを編集するときだけ行う

**`new_note.py`** — type と title を受け取り、対応テンプレートから `Cabinet/Notes/<title>.md` を生成し、frontmatterを埋める。

- 同名ファイルが既にある場合はエラー終了する（現行 `setup` に無かった重複チェック）

**`close_day.sh`** — 締めの機械的部分。

- `Today.md` の frontmatter `date` を読み、`Cabinet/Diary/<date>.md` へ `mv`
- `git add` → 当日分を1コミット
- 日次ブランチを `main` へ fast-forward マージ
- `git push`
- `main` への切り替えに失敗した場合と non-fast-forward の場合は、日次ブランチへ戻り、**締めのコミットを取り消して `Today.md` を元の位置に戻してから**非ゼロ終了する。作業ツリーを締める前の状態に復元することで、人間が `main` 側を解決したあとに同じ手順をもう一度実行できる。復元処理はシェル関数1本にまとめ、2つの経路が同じコードを通るようにする
- 復元は `git reset --soft` と `mv` で行い、作業ツリーを破棄する操作（`git reset --hard` 等）は使わない
- `git push` の失敗では復元しない。`main` へのマージは既に完了しており、巻き戻すとローカルの履歴だけが失われるため。代わりに `git pull --rebase origin main` で解決してから `git push origin main` を実行するよう促して非ゼロ終了する
- `Cabinet/Diary/<date>.md` が既に存在する場合は上書きせず非ゼロ終了する

### スキル

`secretary` 1本。開始／更新／締めの3モードと、貼付本文の取り込み入口を持つ。分類基準の定義はこのファイルにのみ書く。

### カスタムコマンド

`/today`（開始または更新）、`/intake`（貼付本文の取り込み）、`/close`（締め）。いずれも `secretary` スキルを呼ぶだけの薄い入口。

### サブエージェント

会議の事前準備で、当日の会議が **3件以上を目安に**、各会議の過去議事録の探索を Explore に並列委任する。3 は厳密な閾値ではなく、逐次に読むと待たされる件数の目安である。探索範囲は `Cabinet/Notes/` 内のみで、`Documents/` は対象外。読み取り専用に限定し、ノートの書き込みは親が一括で行う。同一ファイルへの並行書き込みを起こさないため。

**並列委任を行うのは開始モードだけとする。** 更新モードは30分間隔で走るため、毎回サブエージェントを起動するのは過剰である。

## 7. 3モードの手順

### モードの判別

`/today` は開始と更新のどちらかに解決される。判別は `Today.md` の有無と、その frontmatter の `date` の2条件で行う。

- `Today.md` が存在しない → **開始モード**
- `Today.md` が存在し、`date` が今日 → **更新モード**
- `Today.md` が存在し、`date` が今日でない → **停止する。** 前日分が締められていない状態なので、人間に報告して締めを促し、自動では先へ進まない。前日の締めが `main` への fast-forward マージ失敗で止まっていた場合、`/close` の再実行は同じ地点で再び失敗するため、`main` 側を先に解決する必要があることも案内に含める

`date` の照合を足す理由は、締めが失敗して前日の `Today.md` が残った翌朝に更新モードへ落ちると、昨日の日付のファイルに今日の予定を書き込み、次の締めで `Cabinet/Diary/<昨日>.md` として2日分が1ファイルに混ざるため。通知を行わない設計なので、人間はこの混入に気づけない。

締めモードは `/close`、または「締めて」「クリアデスク」等の明示的な指示でのみ起動する。時刻による自動締めは行わない。人間が退勤したかどうかを時刻から推定できないうえ、自動締めが `main` への非fast-forwardマージで中断した場合、人間が不在のまま日次ブランチが残るため。

現行 `today/SKILL.md:13-31` はモード判別に5条件・19行を費やし、`Today.md` の有無と `Cabinet/Diary/<今日>.md` の有無と明示指示と22時の4変数を見ていた。2条件に単純化する。

### 開始モード

1. 日次ブランチ `daily/YYYY-MM-DD` を確認・作成する。
2. `Cabinet/Templates/today.md` から `Today.md` を生成する。
3. `Cabinet/MEMORY.md` を読み込む。
4. 前日の `Cabinet/Diary/<前日>.md` に未処理の痕跡（締めが書く `- ⚠ 未処理 N件` の行）があれば、`## メモ` に `- 前日の未処理: [[Cabinet/Diary/<前日>]]` の1行を書く。取りこぼしを翌日に繰り越して見えるようにする。
5. カレンダーを取得する（第8章の契約に従う）。
6. 各イベントについて `index.py --type meeting --date <今日>` の出力を `calendar_event_id` で照合し、無ければ `new_note.py` で議事録ノートを作る。
7. 定例（`calendar_series_id` 一致）は前回の同シリーズ議事録から `## アクション` の未完分と次回議題を転記する。会議3件以上を目安に探索を並列Exploreへ委任する。
8. タスクを抽出する。「今日のタスク」の条件は、`status` が `1_todo` または `2_doing` であり、かつ `due` が今日以前であるか `status` が `2_doing` であること。`index.py --type task --status 1_todo,2_doing` の出力から絞り込む。
9. `## 今日の予定` と `## 今日のタスク` を書く。
10. `/loop` を起動し、更新モードを30分間隔で自走させる。

### 更新モード（`/loop` から30分間隔）

1. 必要な索引を `index.py` で取得する。**個別ノートを1件ずつ読まないことが制約であり、呼び出し回数そのものではない。**1サイクルの `index.py` 呼び出しは数回に収め、ノート件数に比例させない。
2. カレンダーを1回引く。以降のステップは取得済みのイベント一覧を使い回す。
3. `Cabinet/MEMORY.md` を読み込む。分類と `context` の判断が実際に行われるのはこのモードであり、関係者の役割や継続中の前提はここで要る。
4. `## 今日のタスク` のチェック済み行（`- [x]`）を完了の合図として扱い、対応するタスクノートの `status` を `4_done`、`done` を今日の日付にする。状態はノート側の frontmatter が持つため、次の全置換で当該タスクは一覧から外れる。冪等性は保たれる。
5. **カレンダーに新しく現れたイベントの議事録ノートを作る。** 開始モードの第6項と同じ照合・生成を行い、定例なら前回の同シリーズ議事録からの転記も行う。ただし探索の並列Explore委任は開始モードだけとする。日中に会議が追加されたとき、`## 今日の予定` にリンクだけが並んで実体が無い状態を作らないため。
6. 会議のキャンセル判定を行う。**対象は `index.py --type meeting --date <今日>` が返す行のうち `status` が `1_予定` のものに限る。** そのうち `calendar_event_id` が今日のカレンダーに存在しないものを `3_中止` にする。過去日付の議事録には触れない。このモードは前回状態を保存しないため、対象を今日かつ `1_予定` に絞らないと「今日のカレンダーに無い」が「過去の全議事録」と一致し、30分ごとに過去の記録を破壊する。
7. `## 今日の予定` と `## 今日のタスク` を**全置換で再生成**する。行書式は第4章の「Today.md の行書式」に従う。ノートの状態は第4〜6項で先に確定させてから書く。
8. `## メモ` の未処理行（第4章の「処理済みマーカーの判定規約」に従い**行内に `→ [[...]]` を含まない行**。`- 前日の未処理:` で始まる繰越行は対象外）を分類し、`new_note.py` でノート化し、行の後ろにリンクを追記する。
9. `## 確認したいこと` の回答済み行を処理し、ノート化して行を削除する。元になった `## メモ` 行があれば、その行の後ろにもリンクを追記して未処理状態を解消する。
10. **終了時刻を過ぎた会議の事後構造化を行う。** `## メモ` の生メモから `## 決定事項` と `## アクション` を抽出して議事録ノートに書き、アクションはタスクノートとして起票して議事録からリンクする。`status` を `2_実施済` または `4_不参加` に更新する。判断がつかなければ `## 確認したいこと` へ回す。
11. 通知は行わない。

**このモードは冪等である。** 通知を行わないため差分検出が不要になり、前回状態を保存する必要がない。索引から毎回作り直すだけでよい。現行 `update.md:35` が抱えていた「前回状態の保存先が未定義で実装不能」という問題は設計上消滅する。

### 締めモード

1. `index.py --updated-on <今日>` で当日更新されたノートを抽出し、`Today.md` の内容と合わせて MEMORY 昇格判断を行う。持続的文脈があれば `Cabinet/MEMORY.md` に1行追記する。
2. `## 今日の予定` と `## 今日のタスク` を当日の実績サマリーに書き換える。`## メモ` と `## 確認したいこと` は不変。
3. 未処理のメモ行（第4章の判定規約に従う。`- 前日の未処理:` で始まる繰越行は数えない）または未回答の確認事項が残っている場合、`## メモ` の先頭に `- ⚠ 未処理 N件（内訳: メモ X件 / 確認 Y件）` の1行を追記する。
4. `close_day.sh` を実行する。
5. `/loop` を停止する。**`ScheduleWakeup` ツールを `stop: true` で呼ぶ。成否にかかわらず停止する。**

締めが失敗したときに `/loop` を動かし続けてはならない。`close_day.sh` は失敗時に作業ツリーを復元するが、仮に `Today.md` が失われた状態でループが回ると、次の実行がモード判別で開始モードに落ち、新しい `Today.md` を作ったうえで2本目の `/loop` を起動してしまう。失敗は人間の介入を要する状態であり、自動処理を続ける理由がない。

未処理のメモ行や未回答の確認事項は、第3項のサマリー行を足したうえで `Today.md` ごと `Cabinet/Diary/` に退避する。ノートへの強制変換は行わない。現行の「`Inbox/` 残存分を `Review/` へ強制書き出し」の手順は `Inbox/` 廃止により消滅する。

ただし強制変換を消しただけでは、旧構成でその手順が担っていた取りこぼし防止まで一緒に失われる。通知を行わない設計と組み合わさると、人間は「書いたのに何も起きなかった」ことに気づけない。そこで、締めが未処理件数を1行残し、翌朝の開始モードがその痕跡を見つけて新しい `Today.md` に繰越の1行を書く。強制変換のような重い機構は持たず、取りこぼしが翌日に見える状態だけを作る。

MEMORY への追記は `- <内容>（YYYY-MM-DD 記録）` の1行形式とする。

### 取り込み

会話に貼られた本文からノートを作る。`/intake` の入口。旧 `setup` スキルが担っていた新規プロジェクトの起票もここに含める。「〇〇案件を起票して」のような指示は、分類基準で `project` と判定して `new_note.py --type project` を実行する経路になる。

原文は、`task` なら `## 作業ログ`、`know-how` なら `## 状況`、`meeting` なら `## メモ`、`project` なら `## 概要` に残す。

## 8. カレンダー連携の契約

環境によって利用可能なカレンダーMCPが異なるため、スキル側で吸収する。

1. 実行時に利用可能なカレンダーMCPツールを列挙する。
2. 見つかったすべてのソースから当日 00:00–23:59（ローカルタイムゾーン）のイベントを取得し、マージする。
3. イベントの `id` を `calendar_event_id`、`recurringEventId` を `calendar_series_id` に対応させる。
4. **取得できたソースと、失敗・未接続のソースを `## 今日の予定` の直下に必ず明記する。**
5. 既存の meeting ノートに対応するイベントがカレンダーから消えていた場合、そのノートの `status` を `3_中止` にする。
6. **資料をイベントから抽出し、`## 資料` に貼る。** 対象はイベントの `attachments[]`（`title` と `fileUrl`）と `description` 内のURL。`attachments[]` は `title` を持つのでそれを表示名に使い、`[title](fileUrl)` 形式で書く。`description` 内の裸のURLは表示名が得られないのでURLをそのまま貼る。
7. `settings.local.json` にカレンダーMCPツールの事前許可を追加する。無人ループがパーミッションプロンプトで停止しないようにするため。

**Google Drive MCP には依存しない。** この環境の Drive MCP は未認証で、`authenticate` と `complete_authentication` しか公開しておらず、ファイル参照系のツールは OAuth 完了後にしか現れない。認証状態に依存する手順を秘書ループに置くと、未認証のまま無言で失敗する経路が生まれる。カレンダーの `attachments[]` が表示名を直接持つため、Drive を経由する必要はもともと無い。

第4項は、現行のカレンダー連携が「Google Calendarで取得する」の一文だけで未実装のまま放置されていた失敗を再発させないための担保である。取得できていない事実が毎日 `Today.md` に表示される。

本設計時点で、この環境に接続されているMCPは Google Drive / Gmail / Google Calendar のみで、Outlook / Microsoft Graph は無い。

## 9. 分類基準（設計判断の記録）

**この節の内容の正典は `.claude/skills/secretary/SKILL.md` である。** ここに書くのは、その基準をなぜそう決めたかという設計判断の記録であり、実行時に読まれる定義ではない。基準を変えるときは SKILL.md を直し、本節を追随させる。

判定順に評価し、最初に該当したものを採る。

1. **meeting** — カレンダーイベントに対応する、または会議・打合せの記録である。
2. **project** — 複数のタスクを束ね、数週間以上続き、固有名詞で呼ばれる案件である。
3. **task** — 期限または完了条件があり、自分が行う具体的な行動である。
4. **know-how** — 再利用可能な手順・知識であり、行動ではなく参照対象である。

分類と `context` の判断にあたっては `Cabinet/MEMORY.md` を参照する。関係者の役割や継続中の前提が書かれており、`context` の推定に効く。開始・更新・締めのいずれのモードもこのファイルを読む。

`context` は `index.py --contexts` が返す既存値から選ぶ。**既存値に該当が無い場合は、AIが新しい `context` の候補を提案してノートを作る。確認事項には回さない。** 提案したことは `## メモ` の該当行に ` → [[ノート名]]（context: 提案値）` の形で示し、人間が違うと思えば次の指示で直す。この注記が行末に付くため、処理済みの判定は第4章の規約どおり行内で行う。

「該当が無ければ確認事項へ」としないのは、運用初期の既存値がほぼ空であり、そのままではほぼ全てのメモが質問に化けるため。AIが提案し人間が却下する向きにしておく方が往復が発生せず、運用が続く。

### 確信が持てない場合

`## 確認したいこと` に `- <質問>（1回目） →` の形式で1行追加する。回数は行そのものに書く。更新モードは冪等で前回状態を保存しないため、往復回数を数える場所は `Today.md` の行自身以外に無い。

回答が曖昧で再度聞く必要がある場合は `（2回目）` として書き直す。**2回目でも確定しなければ、AIが最も確からしい分類でノートを作成し、その旨をノート本文に1行記す。**

同じ内容の質問が `## 確認したいこと` に既にある場合は追加しない。更新モードは30分ごとに走るため、重複防止が無いと同じ質問が1日に何度も積み上がる。

これは現行 `update.md:25-27` の「確定不能なら残して通知」に往復上限が無く、人間 → Review → 人間 の往復が原理的に無限化しうる問題への対処である。

## 11. 閲覧面（`.base`）

`Cabinet/Bases/` に4本、各2ビュー以内。

| ファイル | ビュー |
|---|---|
| `プロジェクト.base` | 進行中 / 関連ノート（`file.hasLink(this.file)` で絞り `type` でグループ化） |
| `タスク.base` | 期限超過 / 全件棚卸し |
| `議事録.base` | 日付降順 / コンテキスト別 |
| `ノウハウ.base` | 全ノウハウ一覧 / コンテキスト別 |

`.base` はObsidianが内部で評価するものであり、Claude Codeからはフィルタ結果を読めない。したがってAIの判定には一切使わず、人間の閲覧専用とする。AIの判定は `index.py` のみを使う。

## 12. 非目標

- `Documents/` に置かれたファイルをAIが自動検知する仕組みは作らない。ファイル名の走査も内容の読み取りも行わない。したがってドラッグ&ドロップで置いた資料は自動では会議に紐付かない。紐付けたい時は人間がObsidian上で `## 資料` にリンクを貼るか、`## メモ` で指示する。
- 資料の自動紐付けはカレンダーイベント由来（`attachments` と `description`）のみとする。情報源が構造化されており誤紐付けが起きにくいため。
- 会議中の文字起こし連携は行わない。この環境に入力源が無い。
- 通知は一切行わない。会議直前のリマインドはカレンダーアプリ本体に委ねる。

## 13. メリットとデメリット

### メリット

- ループ1回のコストがノート件数に依存しなくなる。100件でも1000件でも索引スクリプト1回で済む。
- 人間が「どこに書くか」を判断する場面が消える。`Today.md` を開くだけになる。
- 分類基準が1か所に定まり、直したいときに直す場所が確定する。
- 機械的処理がスクリプトに落ちるため、締めのgit操作がAIの手順遵守に依存しなくなる。
- 更新モードが冪等になり、状態ファイルが不要になる。
- 分類の往復に上限があるため、人間とAIの往復が無限化しない。

### デメリットと既知のリスク

- `Today.md` が単一障害点になる。人間とAIが同じファイルを編集するため、Obsidianで開きっぱなしにしていると編集が衝突しうる。緩和策として、更新モードが全置換するのは `## 今日の予定` と `## 今日のタスク` の2セクションのみに限定し、人間が書く2セクションは追記しか行わない。
- 会議直前のリマインドが無いため、遅刻防止はカレンダーアプリ本体の通知に依存する。
- vault にスクリプトが3本入り、Obsidianの世界にコードが混ざる。`.claude/` 配下に置くことでObsidianの表示からは隠れる。
- カレンダー連携を環境非依存に抽象化したため、この環境ではOutlook経路を一度も検証できない。第8章第4項の明記によって、未検証のまま気づかない状態にはならないようにしている。
- **最大のリスクは、この設計もまた運用されないことである。** 今回削減した機構は、そのリスクを下げるための投資である。

## 14. 決定の記録

本設計は以下の選択の結果である。

| 論点 | 決定 |
|---|---|
| 中核機能 | 4機能すべて維持。削るのは機構 |
| 稼働モデル | 30分間隔の常時ループを維持 |
| 索引方式 | 索引スクリプト（stale無し・定数コスト） |
| ゾーン構成 | `Today.md` 1枚に統一。`Inbox/`・`Review/` 廃止 |
| Outlook | カレンダー取得を抽象化し、環境差をスキルで吸収 |
| 議事録 | 事前準備＋事後構造化 |
| ノート構造 | 最小骨。更新履歴は project の `## 経緯` のみ |
| 通知 | 行わない |
| メモの処理 | 処理済みはリンクを付けて残す |
| 資料紐付け | `meeting` の `## 資料` から片方向リンク。自動化はカレンダー由来のみ |
| 閲覧面 | `.base` 4本・各2ビュー以内、`Cabinet/Bases/` に配置 |
| 実装割り当て | 機械的＝スクリプト、判断あり＝スキル、入口＝コマンド、並列読み取り＝サブエージェント |

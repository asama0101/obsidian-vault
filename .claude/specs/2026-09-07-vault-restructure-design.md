現行設計は一度も本番運用が回っておらず、利用者の実際の業務規模を検討せずに設計されている。今回はその業務規模を入力にして、スケールとデータモデルの両面を見直す。以下はその根拠となる実データと業務実態である。

## 2. 現状の問題

壊れるのは実行時間ではなく出力量である。現行設計にはこの想定規模に対する保護機構が無い。

### 2-1. スケール

`index.py` の実測（合成vaultで計測、各条件ウォームアップ後3回の中央値）:

| ノート件数 | 全件出力 | 推定トークン | 実行時間 |
|---|---|---|---|
| 500 | 107 KB | 5.4〜7.2万 | 0.14秒 |
| 1,000 | 215 KB | 10.7〜14.3万 | 0.22秒 |
| 3,000 | 652 KB | 32.6〜43.5万 | 0.55秒 |
| 5,000 | 1,087 KB | 54.3〜72.4万 | 0.91秒 |

実行時間は5000件でも0.91秒でボトルネックにならないため、ノートを件数理由で別フォルダへ退避する必要はない。
しかし壊れるのは出力量である。
`SKILL.md:121` の更新モード最終ステップ（今日新規に作った `context` の棚卸し）はフィルタ無しで `index.py` を呼び、これが30分ごと（1日約28回）走るため、ノート1000件で1回10万トークン超になる。
フィルタを付けても安全ではない。
`SKILL.md:101` の今日のタスク抽出が使う `--type task --status 1_todo,2_doing` は、5000件時に393行・71KB（3.6〜4.7万トークン）と試算される。
しかもフィルタは実行時間を減らさない。
`collect()`（`index.py:69-74`）が `Cabinet/Notes/` 配下の全ノートを `read_text()`（`index.py:59`）してから、出力段の `matches()`（`index.py:82-92`）でフィルタする実装になっているためである。
実測でも全件出力とフィルタ付き出力の実行時間差は測定ノイズ範囲（3000件ではフィルタ側が+2.9%遅い）で、支配項は `Path.relative_to().as_posix()`（`index.py:61`）が約32%、`read_text()`（`index.py:59`）が約23%である。
前回設計書 `2026-09-07-vault-secretary-redesign-design.md:418` の「100件でも1000件でも索引スクリプト1回で済む」は**呼び出し回数**の主張であり、出力量には触れていない。

### 2-2. 現行設計に存在しないルール（無いことを確認済み）

- `## 今日のタスク` の件数上限・優先度順・表示打ち切り。抽出条件は `SKILL.md:101` の「`due` が今日以前 **または** `status` が `2_doing`」のみ。ORなので `2_doing` は期限に関係なく全件載る。
- 期限超過タスクの退役・棚上げルール。期限超過は `期限超過 N日` として無期限に再掲される。
- 1日に作る議事録ノートの件数上限。
- `index.py` のデフォルトでの完了物除外。`matches()`（`index.py:82-92`）にその分岐は無い。
- `Cabinet/Notes/` のアーカイブ・退避・retention。`CLAUDE.md:31` がフラット固定を明文で要求している。
- `context` の想定値数・上限・定期統廃合。

## 3. データモデル

note type は現行の4つ（task / project / meeting / know-how）のまま維持する。設備専用のtypeは作らない（不要と判断）。

- project をハブとし、task と meeting が `project: "[[案件名]]"` プロパティで親を指す。know-how だけ project を持たず独立する。複数案件にまたがる場合はリストで複数指定できる（詳細は第4章）。
- 障害対応も project として登録する。専用の incident type は作らない。
- 障害 project の `status` は現行の `1_active` / `2_done` の2値のまま維持する。
- 「復旧したが恒久対策が未完了」は status を増やして表すのではなく、**恒久対策を task として持たせ、その task が残る限り project を `1_active`** とする。
- 値域を障害専用に拡張すると通常案件に無意味な値が混ざり、判断コストが全案件に広がるため。
- `context` プロパティを**廃止**し、Obsidianネイティブの階層タグに置き換える。
- 階層タグの第1階層は次の5つに固定する（閉じた集合）。

| 第1階層 | 例 | 目的 |
|---|---|---|
| `#メーカー/` | `#メーカー/Cisco` | 同一機種の障害・手配履歴の横断 |
| `#領域/` | `#領域/ルーティング` | 設計ノウハウと検証結果の再利用 |
| `#種別/` | `#種別/障害`・`#種別/更改` | 案件の性格の区別 |
| `#ベンダー/` | `#ベンダー/○○電気` | 販社・工事会社の対応履歴 |
| `#設備/` | `#設備/大手町-CoreSW` | 特定設備に紐づく作業の追跡 |

第1階層を固定するのが要点である。フラットな自由タグにすると、`context` が抱えていた「単発値が積み上がる」問題（`SKILL.md:170-175` の規則1/2が抑え込もうとしていたもの）が形を変えて再発する。第1階層が固定なら増えるのは第2階層だけになり、統制が効く。

### タグを付ける対象

タグ第1階層の5軸は変えないが、**付ける対象は type によって絞る**。案件フォルダと `project` プロパティを入れた結果、タグを全ノートに付ける必要がなくなったため。

| type | 付けるタグ |
|---|---|
| project | `#種別/` は必須。`#メーカー/` `#ベンダー/` `#設備/` は該当すれば |
| task・meeting | 原則なし。親案件と違う機器やベンダーが絡んだときだけ、その軸を付ける |
| know-how | `#領域/` が主分類軸。`#メーカー/` も該当すれば |

- メーカーで検索したいとき、project ノートに `#メーカー/Cisco` が付いていればその案件がヒットする。案件が見つかれば配下の task と meeting は `プロジェクト.base` の関連ノートビューで全部見えるため、task・meeting に同じタグを重ねても辿り着ける先は変わらない。
- 判断が発生するのは案件を立てるときと know-how を書くときだけになる。タスクと議事録は日々大量に作られるが、そこでは原則ゼロになる。
- 軸を5つ保ったまま、判断の回数だけを減らせる。

## 4. フォルダ構成

```
vault/
├── Documents/                    ← 投入口のみ。締め完了時点で直下は必ず空
├── Cabinet/
│   ├── Notes/
│   │   ├── <案件名>/             ← project・task・meeting・案件資料を全部ここに
│   │   │   ├── <案件名>.md       ← project ノート（フォルダと同名）
│   │   │   ├── <タスク名>.md
│   │   │   ├── <議事録名>.md
│   │   │   └── 構成図.pdf
│   │   └── *.md                  ← know-how、案件外の task/meeting、案件未確定のもの
│   ├── Reference/                ← 案件横断・長寿命の資料（メーカー資料・規格書）
│   ├── Diary/
│   ├── Assets/
│   ├── Templates/
│   ├── Bases/
│   └── MEMORY.md
```

- `Documents/` は純粋な投入口。人間が直下に放り込み、更新モードが `Cabinet/Notes/<案件名>/` か `Cabinet/Reference/` へ移す。締めで残りを片付け、直下を空にする。
- 行き先が決まらないものは `Documents/未分類/` へ落として直下を空にする。締めのサマリーで未分類の件数を報告する。
- `close_day.sh` にこの検査は**入れない**。既存の検査（デイリーノートの存在・`date` の一致）はデータ破壊を防ぐためのもので、資料の未振り分けはデータ破壊ではない。ここで締めを止めると、急いでいる日に締め自体を放棄することになり害が大きい。
- `project` プロパティはフォルダと**併せて残す**。理由は3つ。
  - `Cabinet/Bases/プロジェクト.base` の「関連ノート」ビュー（`file.hasLink(this.file)`、現行 `プロジェクト.base:21`）はフォルダではなくリンクを見て動いている。プロパティを消すと既存機構が使えなくなる。
  - 複数案件にまたがる会議（「たまにある」とユーザーが回答）を救える。フォルダは親を1つしか持てないが、`project: ["[[A案件]]", "[[B案件]]"]` とリストで書けば、実体は主たる案件のフォルダに置いたまま両方の案件ノートから見える。
  - ファイルを移動してもプロパティは壊れない。正典はプロパティ側で、フォルダはその写像。同期はAIが担保する。
- この案は `.claude/CLAUDE.md:31` の「`type` はフォルダに依存せず判定されるため、フォルダによる分類は不安定な意思決定を強いる」というサブフォルダ禁止の決定を**覆す**（詳細は第10章）。
- 案件フォルダ名は project ノート名と一致させる。案件を改名したときフォルダ名は自動追従しない（Obsidianが追従するのはノートへのリンクだけ）ため、改名時にフォルダも直す処理を締めか更新モードに入れる。
- `Cabinet/Notes/` を件数理由で分割・退避することはしない。第2-1章のとおり実行時間が問題にならないため。

### ノート作成時の初期配置

ノート作成時、案件が確定していれば `Cabinet/Notes/<案件名>/` に、確定していなければ `Cabinet/Notes/` 直下に作る。きっかけによって確定度が違うため、初期の置き場所も変わる。

| きっかけ | 案件の確定度 | 初期の置き場所 |
|---|---|---|
| カレンダーから議事録を作る | 会議名から判定できることが多い | 案件フォルダ |
| `## メモ` から起票したタスク | 不明なことが多い | 直下 |
| 障害の発生 | project がまだ存在しない | project を作ってからその配下 |
| know-how | そもそも案件を持たない | 常に直下 |

- 直下に置いた未確定ノートは、**締めで棚卸しし、案件が決まったものを案件フォルダへ移す**（詳細は第7章）。これをしないと直下が「案件が決まったのに移されていないノート」の吹き溜まりになり、案件フォルダを導入した意味が薄れる。
- 移動してもリンクはObsidianが追従するため壊れない。
- 締めは既に人間の判断を集める場所（期限見直し・`Documents/` の片付け）になっているため、同じタイミングで拾うのが自然。
- 代償として、締めのステップが1つ増え、移動処理が故障点になりうる。

## 5. Bases

現行の4本（`Cabinet/Bases/プロジェクト.base`・`タスク.base`・`議事録.base`・`ノウハウ.base`）のうち、`groupBy: context` を使っている2本（`ノウハウ.base:21-23`・`議事録.base:22-24`）は作り直しが要る。

多値タグの `groupBy` は1ノートが複数グループに現れない（第8章の検証事項1参照）ため、**軸ごとに view を定義し `filters` で絞る方式**に切り替える。

```yaml
views:
  - type: table
    name: Cisco
    filters:
      and:
        - type == "know-how"
        - file.hasTag("メーカー/Cisco")
```

階層タグなので `file.hasTag("メーカー")` と書けば配下すべてを拾える（第8章の検証事項2参照）。

- この方式は tags の `groupBy`（1.10.1以降で対応）に依存しないため、バージョン依存が消える。この環境のObsidianバージョンは特定できていない（`.obsidian/core-plugins.json` に `"bases": true` があるため1.9.0以降であることのみ確定）ため、実利がある。
- `プロジェクト.base` の「関連ノート」ビュー（`file.hasLink(this.file)`、`プロジェクト.base:21`）はそのまま親子ビューとして機能する見込み。
- 代償: `groupBy` は値が増えれば自動でグループが増えたが、view方式では軸の値が増えるたびに `.base` へ view を1本足す編集が要る。`Cabinet/Bases/` は現行「人間の閲覧専用」だったが、Claude Codeが編集する対象に変わる。編集は締めのタイミングで行う（第7章の締めモード拡張を参照）。

## 7. スキルの変更

`.claude/skills/secretary/SKILL.md` を対象とする。

### 出力量の削減（最優先）

- `SKILL.md:121` の全件呼び出しを**廃止**し、`--updated-on <今日>` ベースに置き換える。これは「今日新規に作った `context` の棚卸し」のためだったが、タグ化で棚卸し自体が変わる。単独で最大の効果（1000件時に1回10万トークン超が当日更新分だけになる）。
- `## 今日のタスク` の抽出（現行 `SKILL.md:101`）は `--due-before <今日>` で期限到来分、`--status 2_doing` で進行中分を別々に取る。それぞれ小さく、合計しても現行の一括取得より軽い。

### デイリーノートの予定行の変更

`## 今日の予定` の生成ロジックを変更する。`## 今日の予定` に載せるイベントと、議事録ノートを作るイベントは**完全に一致させる**。判定はすべて機械的に行い、AIの推測を要しない。

**載せる（＝議事録ノートも作る）**

次の3条件をすべて満たすイベントだけを載せる。

- 時刻指定がある（`start.dateTime` を持つ。`start.date` のみの終日イベントは対象外）。
- 自分の `responseStatus` が `declined` でない。
- `attendees` に自分以外の参加者が存在する。

行書式は常に `- [ ] HH:MM-HH:MM [[議事録ノート名]]` の1種類だけになる。チェックボックスなしの行は存在しない。

チェック済みの行を出席の合図として扱う。更新モードがまずチェック済み行を読んで対応する議事録ノートの `status` を `2_実施済` にし、そのあとで `## 今日の予定` を全置換で再生成する。動作は `## 今日のタスク` のチェック処理と同じ形。状態はノート側のfrontmatterが持つため、全置換してもチェックは復元され冪等性が保たれる。

**載せない（完全除外）**

- 終日イベント（`start.date` のみで `start.dateTime` を持たないもの）。休暇・当番などが該当する。
- 自分の `responseStatus` が `declined` のイベント。出席しないため記録する対象がない。
- `attendees` が自分だけ、または `attendees` が存在しないイベント。作業ウィンドウのブロック予定・個人の予定・リマインダーが該当する。

代償: 終日イベントを除外するため、休暇・当番・全社作業日といった終日で登録される予定はデイリーノートに現れない。これらをデイリーノートで見たい場合は、時刻指定のイベントとして登録する必要がある。

未チェックのまま終了時刻を過ぎた行の扱いは、次節「締めモードの拡張」で扱う。

### 締めモードの拡張（既存5ステップに4つ追加）

締めのステップは既存5＋追加4の合計9になる。

| | ステップ | 人間の判断 |
|---|---|---|
| 既存1 | 当日更新分の取得 | 不要 |
| 既存2 | 予定・タスクを実績サマリーへ書き換え。未チェックのまま終了時刻を過ぎた会議行は「不参加でよいか」の確認に回す | 要 |
| 既存3 | `## メモ` `## 確認したいこと` の未処理棚卸し | 要 |
| 既存4 | MEMORY.md への昇格判断 | 要（該当時のみ） |
| 既存5 | `close_day.sh` の実行 | 不要 |
| 追加6 | 期限の見直し | 要 |
| 追加7 | `Documents/` 直下の片付け | 要 |
| 追加8 | `Cabinet/Bases/` の view 追加 | 不要 |
| 追加9 | 直下の未確定ノートを案件フォルダへ移動 | 要 |

- **予定の実績サマリー化に伴う出欠確認**。終了時刻を過ぎても未チェックの会議行は、出席したがチェックし忘れた場合を拾うため、締めのまとめ確認に「不参加でよいか」として出す。人間の回答に応じて `status` を `2_実施済` または `4_不参加` に確定する。
- **期限の見直し**。期限超過タスクと、長く `2_doing` のまま止まっているタスクを一覧し、各件に「翌日 / 今週内 / 保留に落とす / 中止」の提案を根拠付きで添える。人間は違うものだけ直す。これで `due` が実態を反映し続けるため、件数上限という対症療法が不要になる。
- **`Documents/` 直下の片付け**。更新モードで判定しきれなかったファイルの行き先を確認し、直下を空にする。
- **`Cabinet/Bases/` の view 追加**。タグの第2階層に新しい値が生まれた日は、対応する view を `.base` に足す。
- **直下の未確定ノートを案件フォルダへ移動**。`Cabinet/Notes/` 直下にある task・meeting のうち案件が決まったものを一覧し、移動先の案件フォルダを確認してから移す。案件がまだ決まらないものは直下に残す。

**問題はステップ数ではなく人間との往復回数である。** 9ステップのうちAIだけで完結するのは3つ（既存1・既存5・追加8）で、残り6つ（既存2・既存3・既存4・追加6・追加7・追加9）が人間の判断を要する。1つずつ順に聞くと締めが6往復になり、毎日実行するのは現実的でない。そこで**判断を要する6項目を1つの確認としてまとめて提示し、人間が1回答えれば全部片付く形にする**。ステップ数は9のままだが往復は1回になる。全体を見てから判断できる分、判断もしやすくなる。

これは放置できない問題である。締めをしないと翌日が止まる。モード判別表では前日の日次ブランチに居残ったまま `/today` を起動すると停止し、先に `/close` するよう促される。締めが未締めの証拠を兼ねる設計のため、締めを飛ばすと翌朝の秘書ループが立ち上がらない。

### 更新モードの追加

- `Documents/` 直下を見て、判定できるものを `Cabinet/Notes/<案件名>/` か `Cabinet/Reference/` へ振り分ける。判定できないものは直下に残し、`## 確認したいこと` に質問として出す。推測で振り分けない。

### タグ規則

`context` の規則1/2（`SKILL.md:170-175`）をタグ規則に差し替える。

### スキルの分割

- 締めモードの詳細手順を `references/close.md` に出す。締めは1日1回しか使わないため、開始と更新のたびに読み込む必要がない。
- 開始・更新モードとタグ規則・ノート配置ルールは `SKILL.md` 本体に残す。ほぼ毎回参照するため。
- 分割の基準は**使用頻度**。

## 10. 覆す既存決定

`.claude/CLAUDE.md:31`「`Cabinet/Notes/` はサブフォルダを作らずフラットに保つ。`type` はフォルダに依存せず判定されるため、フォルダによる分類は不安定な意思決定を強いるだけになる。」を覆す。

- 覆す理由: project をハブにした案件フォルダ構成（第4章）は、案件配下に task・meeting・資料を集約することで、案件単位の閲覧・資料紐付けを成立させるために要る。フラット構成のままではこれができない。
- 覆される指摘自体は正しい。フォルダ構成を導入すると「ノートを作るたびに案件配下か直下かを判断する必要」という代償が残る。
- 代償への対処: 案件が確定していれば `new_note.py --project` で自動的に案件フォルダへ配置できる。確定前のものは直下に作り、確定後に移す。`type` の判定はフォルダに依存させず、引き続き frontmatter の `type` プロパティで行う（この点は覆さない）。フォルダはあくまで置き場所の分類であり、判定基準ではない。

`.claude/CLAUDE.md:73`「チェックボックスを使うのは `## 今日のタスク` だけ。（中略）予定側は押しても意味を持たせる先が無いため素の箇条書きにする。」を覆す。

- 覆す理由: meeting には `status`（`1_予定` / `2_実施済` / `3_中止` / `4_不参加`）があり、チェックは `2_実施済` に素直に対応する。「意味を持たせる先が無い」という前提が誤っていた。
- 解消される問題: 現行の `SKILL.md:113`（更新モードのステップ10）は終了時刻を過ぎた会議について「`status` を `2_実施済` または `4_不参加` に更新する。判断がつかなければ `## 確認したいこと` へ回す」となっており、AIが利用者の出欠を推測している。チェックボックス化（第7章「デイリーノートの予定行の変更」）によりこの推測が不要になる。

`SKILL.md:186-189` のカレンダー節を覆す。現行は「見つかったすべてのソースから当日 00:00–23:59（ローカルタイムゾーン）のイベントを取得してマージする」（`SKILL.md:188`）とだけ定め、取得したイベントを絞る記述を一切持たない。`SKILL.md:99`（開始モードのステップ6）が各イベントを `calendar_event_id` で照合して一致が無ければ議事録ノートを作るため、当日のカレンダーに存在する全イベントが1件1ノートの議事録になっていた。

- 覆す理由: 実際のカレンダーには終日予定（休暇・当番）、作業ウィンドウのブロック予定、自分が辞退した通知系イベント、個人の予定が含まれる。絞り込みが無いとこれらが全部議事録ノートとして生成され、実体を持たないノートが年間数百件単位で積み上がる。
- 追加する絞り込み: `## 今日の予定` への記載対象と議事録ノート生成対象の両方を、第7章「デイリーノートの予定行の変更」の3条件（時刻指定がある・辞退していない・自分以外の参加者がいる）で機械的に絞り込む。2つの対象は完全に一致させるため、絞り込み条件は1本で済む。

```markdown
## メモ

- 先方から大手町の停止調整、10月後半で押さえたいと連絡 → [[大手町DC コアSW更改]]（経緯に追記）

```

3行がそれぞれ違う扱いになった理由を挙げる。

- 1行目は既存 project への追記なのでノートを作らず、`## 経緯` に書いた旨だけを追記する。
- 2行目は新規タスクなので捕捉としてノート化し、` → [[ノート名]]` を追記する。
- 3行目は既存ノートへの `status` 変更指示なので直接実行し、` → 実行済み（何をしたか）` を追記する。
- `⚠` と `ⓘ` で始まる行はAIが書いた行なので処理対象にならない。人間が書いた行だけを処理する。

# secretary

Obsidian vaultで秘書業務を回す。人間との接点はデイリーノート1枚だけ、`Cabinet/Notes/` の一覧取得は `index.py` だけ、分類基準はこのファイルだけ。

デイリーノートは `Cabinet/Diary/<今日の日付>.md` である。作成時からこの場所に置き、以後移動しない。

## モードの判別

締めと取り込みは他の条件と直交するため、先に判定する。

- 「締めて」「クリアデスク」等の明示指示 → **締めモード**
- 会話にメール・チャット等の本文が貼られている → **取り込み**
- どちらでもない場合は、`git branch --show-current` でブランチを確認してから、当日ファイルの有無と組み合わせて下の表で判定する。

| 現在のブランチ | `Cabinet/Diary/<今日>.md` | 判定 |
|---|---|---|
| `main` | 無し | 開始モード |
| `main` | 有り | 開始モード（ブランチだけ作り直す。締めが成功した後に同じ日でもう一度 `/today` を実行した場合、または締めが push で失敗して `main` 上に残った場合） |
| `daily/<今日>` | 有り | 更新モード |
| `daily/<今日>` | 無し | 開始モード（前回の開始がブランチ作成後に中断した場合。既存ブランチを使い回す） |
| `daily/<今日以外>` | — | **停止**。前日分が未締め |
| 上記以外 | — | **停止**。想定外のブランチ |

判別をブランチで行うのは、デイリーノートを最初から `Cabinet/Diary/` に作るため。過去分も常に同じ場所にあるので、ファイルの存在では前日未締めを検知できない。締めは必ず `main` 上で終わるため、日次ブランチに居残っていること自体が未締めの証拠になる。

表の2行目（`main` かつ当日ファイル有り）は、締めが成功した直後に同じ日でもう一度 `/today` を実行したときにも起きる。締めは HEAD を `main` に残すので、この経路が最も頻度が高い。このとき開始モードが走るが、既存の当日ファイルは作り直さずそのまま使い（開始モードの第2項）、`## 今日の予定` と `## 今日のタスク` だけが全置換で再生成される。`## メモ` と `## 確認したいこと` は全置換の対象外なので、人間が書いた内容はそのまま残る。

**停止**と判定した場合は人間に報告し、自動では先へ進まない。報告する内容は次のとおり。

- `daily/<今日以外>` の場合: 「`<ブランチ名の日付>` 分が締められていない」と伝え、`Cabinet/Diary/<ブランチ名の日付>.md` の有無で復旧手順を書き分ける。
  - ファイルが有る場合: 「`/close` で締めてから `/today` を実行すること」と伝える。
  - ファイルが無い場合: 「`git checkout main` で `main` へ戻ってから `/today` を実行すること」と伝える。この行の判定は当日ファイルの有無を問わないため、開始モードがブランチ作成直後に中断して日をまたぐとこの状態に到達する。締めるべき記録が無いので締める必要はなく、`/close` を打っても `<ファイル名> がありません` で終了コード1になる。
  - あわせて、前日の締めが `main` への fast-forward マージ失敗で止まっていた場合は `/close` を再実行しても同じ地点で再び失敗するため、先に `main` 側を解決する必要があることも伝える。
- 想定外のブランチの場合: 現在のブランチ名を示し、`main` か当日の日次ブランチへ移ってから `/today` を実行するよう伝える。

締めは時刻では起動しない。人間が退勤したかを時刻から推定できないため。

## 共通の前提

- ノートを作成・編集する前に、日次ブランチ `daily/<今日の日付>` にいることを確認する。存在の判定は `git branch --list daily/<今日の日付>` で行い、出力が空なら `main` から `git checkout -b daily/<今日の日付>` で作る。出力があれば作らず `git checkout daily/<今日の日付>` で移る。
- 日中はコミットしない。締めが1コミットにまとめる。
- `Cabinet/Notes/` を1件ずつ読んではいけない。一覧が要るときは必ず `index.py` を使う。個別のReadは、実際にそのノートを編集するときだけ行う。
- 通知は一切行わない。伝えたいことはデイリーノートに書く。

## デイリーノートの行書式

更新モードは `## 今日の予定` と `## 今日のタスク` を毎回全置換で再生成するため、書式を固定しないと出力が日々揺れる。

- `## 今日の予定`: `- HH:MM-HH:MM [[議事録ノート名]]`。終日予定は時刻を `終日` とする。セクション末尾に `（取得元: ...）` の1行を置く。チェックボックスは使わない。予定にチェックを入れても意味を持たせる先が無いため。
- `## 今日のタスク`: `- [ ] [[タスクノート名]] <状態>`。`<状態>` は `期限 今日` / `期限超過 N日` / `進行中` のいずれか。ここだけはチェックボックスを使う。人間がチェックした行を更新モードが完了の合図として読むため。
- `## 確認したいこと`: `- <質問>（N回目） →`。
- `## メモ`: 人間の自由記述。捕捉してノート化した行は元の文言の後ろに ` → [[ノート名]]` を足す。`context` の新しい値を提案した場合は ` → [[ノート名]]（context: 提案値）` となる。既存ノートへの操作指示として直接実行した行は ` → 実行済み（<何をしたか>）` を足す。

### 処理済みマーカーの判定規約

**この節がAI/人間の行判定に関する正典である。** `.claude/CLAUDE.md` と設計書はここを参照する。

`## メモ` の行には、**AIが書いた行**と**人間が書いた行**の2種類がある。

- AIが `## メモ` に書く行は、必ず次のいずれかの接頭辞を持つ: `- ⚠ `（警告。締めの未処理棚卸しが書く）、`- ⓘ `（情報。今日新規に作った `context` の棚卸しが書く）、`- 前日の未処理: `（繰越。開始モードが書く）。
- **これらの接頭辞で始まる行は、処理対象にしない。未処理件数にも数えない。** 人間の依頼ではなく、AIが自分の都合で書いた行のため。
- 人間が書いた行は、**行内に `→ [[...]]` または `→ 実行済み` を含むものが処理済み、含まないものが未処理**と判定する。行末では判定しない。`context` を提案した行は行末が `（context: 提案値）` になるため、行末で判定すると毎サイクル未処理と誤判定され、同じ行から何度もノートを作ろうとして `new_note.py` が同名衝突で終了コード1を返す。
- **今後AIが `## メモ` に新しい種類の行を書く必要が生じた場合は、必ず上記の接頭辞のいずれかを使う。新しい接頭辞を増やさない。** 接頭辞を1つずつ列挙して判定する方式は、新しい行の種類が増えるたびに見落としを繰り返す（実際に3回発生した）。判定規約そのものを「AI行は接頭辞で判別、人間行は `→` マーカーで判別」という2分法に一般化することで、新種の行が増えても判定規約を変えずに済むようにする。

## スクリプト

```bash
# 索引（列: path type status due done context date title mtime calendar_event_id calendar_series_id、ヘッダ行なし、11列）
python3 .claude/scripts/index.py [--type task,meeting] [--status 1_todo,2_doing] \
    [--date 2026-09-07] [--updated-on 2026-09-07] [--contexts]

# ノート生成（vault相対パスを標準出力に返す。既存なら終了コード1）
python3 .claude/scripts/new_note.py --type task --title "見積書の作成" \
    --set due=2026-09-10 --set context=A社

# 締め（コミット・ffマージ・push）
bash .claude/scripts/close_day.sh

# context の値を一括で付け替える（変更したノートのvault相対パスを1行ずつ返す）
python3 .claude/scripts/rename_context.py --old A社案件 --new A社 [--dry-run]

# context が空のノートに後から値を付ける（--old ""は使えないため--pathで指定する。複数回指定可）
# 規則2の典型形: 2件目はnew_note.py --set context=A社で直接作り、1件目にだけ遡って付ける
python3 .claude/scripts/rename_context.py --path "Cabinet/Notes/1件目.md" --new A社
```

## 開始モード

1. 日次ブランチを確認・作成する。
2. `Cabinet/Templates/today.md` から `Cabinet/Diary/<今日の日付>.md` を作り、`date` を今日にする。同名のファイルが既にあれば作り直さず、そのまま使う（`main` 上に当日分が残っていた場合。書きかけの `## メモ` を消さないため）。
3. `Cabinet/MEMORY.md` を読む。
4. 前日の `Cabinet/Diary/<前日>.md` に未処理の痕跡（`- ⚠ 未処理 N件` の行）があれば、`## メモ` に `- 前日の未処理: [[Cabinet/Diary/<前日>]]` の1行を書く。取りこぼしを翌日に繰り越して見えるようにするため。
5. カレンダーを取得する（下の「カレンダー」参照）。
6. 各イベントを `index.py --type meeting --date <今日>` の出力の `calendar_event_id` 列と照合し、一致が無ければ `new_note.py --type meeting --title "<今日の日付> <会議名>" --set calendar_event_id=<イベントのid> --set calendar_series_id=<recurringEventId>` で作る。ノート名は `YYYY-MM-DD 会議名` とする（定例会議は毎回同じイベント名を持つため、日付を含めないと2回目の生成が同名衝突で終了コード1になる）。イベントに `recurringEventId` が無い（単発イベントである）場合は `--set calendar_series_id=...` を渡さず、`calendar_series_id` は空のままにする。`## 資料` をイベントから埋める。
7. 定例（`calendar_series_id` が一致）は前回の同シリーズ議事録から `## アクション` の未完分と `## 議題` を転記する。当日の会議が3件以上を目安に、各会議の過去議事録探索を Explore サブエージェントへ並列委任する。探索範囲は `Cabinet/Notes/` のみ。書き込みは自分が行う。並列委任を行うのは開始モードだけとする（更新モードは30分ごとに走るため、サブエージェントの起動は過剰になる）。
8. `index.py --type task --status 1_todo,2_doing` を叩き、`due` が今日以前のもの、または `status` が `2_doing` のものを今日のタスクとする。
9. `## 今日の予定` と `## 今日のタスク` を書く。
10. `/loop` を30分間隔で起動し、更新モードを自走させる。

## 更新モード

1. 必要な索引を `index.py` で取得する。**個別ノートを1件ずつ読んではならない。**これが本来の制約であり、呼び出し回数そのものではない。1サイクルの `index.py` 呼び出しは数回に収め、ノート件数に比例させない。
2. カレンダーを1回だけ引く。以降のステップは取得済みのイベント一覧を使い回す。
3. `Cabinet/MEMORY.md` を読む。分類と `context` の推定に使う。
4. **`## 今日のタスク` のチェック済み行（`- [x]`）を完了の合図として扱う。** 対応するタスクノートの `status` を `4_done`、`done` を今日の日付にする。状態はノート側の frontmatter が持つため、次のステップの全置換で当該タスクは一覧から外れる。冪等性は保たれる。
5. **カレンダーに新しく現れたイベントの議事録ノートを作る。** 開始モードのステップ6と同じ照合・生成を行う（`index.py --type meeting --date <今日>` の `calendar_event_id` 列と照合し、無ければ `new_note.py` で作る）。定例なら前回の同シリーズ議事録から `## アクション` の未完分と `## 議題` を転記する。**ここでは Explore への並列委任は行わない。** 日中に会議が追加されたとき `## 今日の予定` にリンクだけが並んで実体が無い状態を作らないため。
6. **会議のキャンセル判定を行う。** 対象は `index.py --type meeting --date <今日>` が返す行のうち `status` が `1_予定` のものだけに限る。そのうち `calendar_event_id` が今日のカレンダーに存在しないものを `3_中止` にする。**`date` が今日でない過去の議事録には絶対に触れない。** このモードは前回状態を保存しないため、対象を今日かつ `1_予定` に絞らないと「今日のカレンダーに無い」＝「過去の全議事録」となり、30分ごとに過去の記録を書き換えてしまう。
7. `## 今日の予定` と `## 今日のタスク` を**全置換で再生成**する。開始モードと同じ抽出条件を使う。ステップ4〜6でノートの状態を先に確定させてから書くため、リンク切れも完了済みタスクの再掲も起きない。
8. `## メモ` の未処理行（上の「処理済みマーカーの判定規約」に従い、AIの接頭辞（`⚠`/`ⓘ`/`前日の未処理:`）を持たず、かつ `→ [[...]]` や `→ 実行済み` を含まない行）を1行ずつ次のいずれかとして処理する。
   - **既存ノートへの操作指示**として扱うのは、次の両方を満たす場合に限る（既定は捕捉なので、この条件は狭く取る）: (1) 変更内容が `context` の付け替え・`status` の変更・`due` の変更のいずれかである、(2) メモ行が既存ノートを `[[リンク]]` で名指ししているか、既存ノートの `title` と一致する語を含んでいて対象ノートが一意に特定できる。「A社の件は来週まで延期」のように読み方が割れる行は、リンクも `title` 一致も無ければ操作指示と誤解釈しない。誤って操作指示扱いすると、ノートが作られないまま ` → 実行済み` が付いて処理済み扱いになり、`status`/`due` の誤実行が締めの未処理棚卸しにも表れず検知経路を失うため。
     操作指示と判定した場合は、ノート化せず**指示として直接実行する**。実行後、行の後ろに ` → 実行済み（<何をしたか>）` を追記する。`context` の**値→値の付け替え**（「XをYにして」）は `rename_context.py --old X --new Y` を使う。**特定のノートにだけ値を付ける・外す**（`context` が空のノートに付ける等、対象ノートを名指しする）場合は `--path` を使う。判断の目安は「旧い値が分かっているなら `--old`、対象ノートを名指しするなら `--path`」。ノートの削除や本文の書き換えは対象外とし、その種の指示は会話で受ける。
   - 上記の条件を満たさない場合は**捕捉**として扱う（既定）。`new_note.py` でノート化し、行の後ろに ` → [[ノート名]]` を追記する。
9. `## 確認したいこと` の回答済み行（`→` の右に文字がある行）を処理し、ノート化してその行を削除する。元になった `## メモ` 行があれば、その行の後ろにも ` → [[ノート名]]` を追記して未処理状態を解消する。
10. **終了時刻を過ぎた会議の事後構造化を行う。** `## メモ` の生メモから `## 決定事項` と `## アクション` を抽出して議事録ノートに書き、アクションはタスクノートとして起票して議事録からリンクする。`status` を `2_実施済` または `4_不参加` に更新する。判断がつかなければ `## 確認したいこと` へ回す。
11. **今日新規に作った `context` の棚卸しを行う。このステップは更新モードの最後に置く。**
    - 対象の判定: `index.py` の全出力を使い、その `context` 値を持つノートが**すべて今日更新されている**（`mtime` の日付部分が今日）ものを「今日新規に作った `context`」とする。空文字列は対象外とする（`index.py --contexts` も空を落とす仕様に揃える）。
    - 出力: 該当があれば `## メモ` の先頭に `- ⓘ 今日作った context: <値1>, <値2>（違っていれば rename_context.py で付け替え）` の1行を追記する。該当が無ければ何もしない。
    - **値は昇順に並べる。** `index.py --contexts` の `sorted()` に揃えるため。並び順が揺れると `A社, B社` と `B社, A社` が毎サイクル「構成が変わった」と誤判定される。
    - **同じ内容の行が既に `## メモ` にある場合は追加しない。値の構成が変わっていれば、既存のⓘ行を書き換える。**
    - 判定に `date`（作成日）ではなく `mtime`（更新日）を使うのは、規則2で1件目に遡って `context` を付ける場合、1件目の `date` は過去日付のままだが、その編集によって `mtime` は今日になるため。`date` 基準では1件目が拾われず検知漏れになる。
    - この判定は索引1回で計算でき、前回状態の保存は不要（状態ファイルを新設しない）。
    - 既知の限界として、次の場合も同じ条件を満たし、新規として再掲されうる。情報提供の1行なので実害は無い。
      - 確立済みの `context` でも、その値を持つ全ノートがたまたま同じ日に更新された場合
      - その `context` を持つノートが1件しか無い場合
      - 当日 `rename_context.py` で付け替えた既存値の場合
    - **締めモードではなく更新モードに置くのは、締めモードで書くと人間の目に触れないためである。** 締めは人間がその日のデイリーノートを見終わったあとに走るため、そこで書いた行は誰にも読まれないまま過去分になる。更新モードなら30分ごとのサイクルで書かれ、人間がその日のうちに見られる。
    - **更新モードの最後に置くのは**、ステップ9・10より前に置くと、それらのステップが新しい `context` を作った場合（確認事項の回答からのノート化、会議の事後構造化からのタスク起票）にそのサイクルで告知されず、その日の最後のサイクルでは翌朝まで告知されないため。

このモードは冪等である。前回の状態を保存する必要はない。

`## メモ` と `## 確認したいこと` に対しては追記と処理済み行の削除だけを行い、人間が書いた文言を書き換えない。ただしAI自身が書いた `⚠` 行・`ⓘ` 行の書き換え（内容変化時の上書き）はこの制約の対象外とする。人間の文言ではないため。

## 締めモード

1. `index.py --updated-on <今日>` とデイリーノートの内容から、`Cabinet/MEMORY.md` へ昇格すべき持続的文脈があるか判断する。あれば `- <内容>（YYYY-MM-DD 記録）` の形式で1行追記する。**同じ内容の行が既にあれば追記しない。** `close_day.sh` が非fast-forwardマージ等で失敗して復元（`git reset --soft`）したあと `/close` を再実行する経路では、前回の追記がファイルに残ったままもう一度この判断を行うため、重複防止が無いと同じ行が2行以上並ぶ。
2. `## 今日の予定` と `## 今日のタスク` を当日の実績サマリーに書き換える。`## 確認したいこと` と `## メモ` は変えない。
3. **未処理の棚卸しを行う。** 未処理のメモ行（「処理済みマーカーの判定規約」に従い、AIの接頭辞（`⚠`/`ⓘ`/`前日の未処理:`）を持たず、かつ `→ [[...]]` や `→ 実行済み` を含まない行）または未回答の確認事項（`→` の右が空の行）が残っている場合、`## メモ` の先頭に `- ⚠ 未処理 N件（内訳: メモ X件 / 確認 Y件）` の1行を追記する。**ⓘ行と同じ重複防止を行う。同じ内容の行が既にあれば追加せず、件数が変わっていれば既存の⚠行を書き換える。** ffマージ失敗→復元→`/close`再実行の経路で締めが複数回走ると、重複防止が無ければ⚠行が並んでしまう。
4. `bash .claude/scripts/close_day.sh` を実行する。
5. **`/loop` を停止する。`ScheduleWakeup` ツールを `stop: true` で呼ぶ。** 成否にかかわらず停止する。失敗は人間の介入を要する状態であり、自動処理を続ける理由が無いため。

未処理のメモ行や未回答の確認事項は、上のサマリー行を足したうえでデイリーノートにそのまま残す。強制的なノート変換は行わない。翌朝の開始モードが前日のデイリーノートにこの `- ⚠ 未処理` 行を見つけると、新しいデイリーノートの `## メモ` に繰越の1行を書く。取りこぼしが黙って消えないようにするための最小限の仕掛けである。

## 取り込み

会話に貼られた本文からノートを作る。

1. 依頼内容・締切・関連する案件を読み取る。
2. 下の分類基準で `type` と `context` を決める。旧 `setup` スキルが担っていた新規プロジェクトの起票もこの経路に含まれる。「〇〇案件を起票して」のような指示は、分類基準で `project` と判定して `new_note.py --type project` を実行する経路になる。
3. `new_note.py` でノートを作り、原文全体を `task` なら `## 作業ログ`、`project` なら `## 概要`、`meeting` なら `## メモ`、`know-how` なら `## 状況` に残す。
4. 作ったノートのパスを人間に伝える。

## 分類基準

判定順に評価し、最初に該当したものを採る。

1. **meeting** — カレンダーイベントに対応する、または会議・打合せの記録である。
2. **project** — 複数のタスクを束ね、数週間以上続き、固有名詞で呼ばれる案件である。
3. **task** — 期限または完了条件があり、自分が行う具体的な行動である。
4. **know-how** — 再利用可能な手順・知識であり、行動ではなく参照対象である。

判断にあたっては `Cabinet/MEMORY.md` を参照する。関係者の役割や継続中の前提が書かれており、特に `context` の推定に効く。

`context` は `index.py --contexts` が返す既存値から選ぶ。既存値に該当が無い場合は次の2規則に従う。確認事項には回さない。

- **規則1（単発は空にする）**: `context` は繰り返し現れるまとまり（取引先・案件領域・定常業務）を指す軸であり、1件しか属さないものには値を付けない。`context` は全typeで任意プロパティなので、空欄のままにしてよい。
- **規則2（2件目で新しい値を作る）**: 既存値に該当が無い場合、1件目は `context` を空のままノートを作る。**同じテーマの2件目が現れたかどうかは、`index.py` の `title` 列・`context` 列、および `Cabinet/MEMORY.md` を使って判定する。** `title` に共通の固有名詞（社名・案件名・人名）が現れる場合、または `MEMORY.md` にその関係が書かれている場合に同テーマとみなす。**判断がつかなければ同テーマとみなさない**（両方 `context` は空のまま残す）。後から `rename_context.py --path` で付けられるため、誤って束ねるより空のまま残す方が安全である。同テーマの2件目が現れたと判断した時点で、初めて新しい `context` の候補を自分で決める。**2件目は `new_note.py --set context=<新しい値>` で最初から値を付けて作る。1件目にだけ `rename_context.py --path <1件目のパス> --new <新しい値>` で遡って付ける。** frontmatterの直接編集は行わない（機械的な書き換えはスクリプトに寄せる。1件目は `context` が空で `rename_context.py --old ""` は誤操作防止のため終了コード2で拒否される仕様のため、`--path` 経路を使う）。

新しい値を付けたときだけ `## メモ` の該当行に ` → [[ノート名]]（context: 提案値）` の形で示す。人間が違うと思えば次の指示で直せばよい。1件目を空のままにした場合はこの注記を付けず、通常どおり ` → [[ノート名]]` だけを追記する。**規則2で2件目をきっかけに1件目へ遡って値を付けたときは、1件目のメモ行がまだ当日のデイリーノートに残っていれば、その行にも `（context: 提案値）` を追記する。** 1件目が前日以前に作られていた場合、そのメモ行は前日以前のデイリーノートにあるため追記しない（過去のデイリーノートは書き換えない）。この注記が行末に付く場合があるため、処理済みの判定は行末ではなく行内で行う（上の「処理済みマーカーの判定規約」を参照。判定ロジック自体は変えない）。

既存値が少ない運用初期に「該当が無ければ確認事項へ」とすると、ほぼ全てのメモが質問に化けて往復が発生する。AIが提案して人間が却下する向きにしておく方が運用が続く。規則1・規則2は、新しい値を作る前に「空欄のままでよいか」を先に検討させ、単発値が `index.py --contexts` の出力に積み上がり続けるのを防ぐ。

### 確信が持てないとき

`## 確認したいこと` に `- <質問>（1回目） →` の形式で1行追加する。回数は行そのものに書く。更新モードは冪等で前回状態を保存しないため、往復回数を数える場所はデイリーノートの行自身以外に無い。

回答が曖昧で再度聞く必要がある場合は `（2回目）` として書き直す。**往復の上限は2回とする。2回目でも確定しなければ、最も確からしい分類でノートを作り、その旨をノート本文に1行記す。** 人間とAIの往復を無限化させないため。

同じ内容の質問が `## 確認したいこと` に既にある場合は追加しない。更新モードは30分ごとに走るため、重複防止が無いと同じ質問が1日に何度も積み上がる。

## カレンダー

1. 実行時に利用可能なカレンダーMCPツールを列挙する。
2. 見つかったすべてのソースから当日 00:00–23:59（ローカルタイムゾーン）のイベントを取得してマージする。
3. イベントの `id` を `calendar_event_id`、`recurringEventId` を `calendar_series_id` に対応させる。
4. **取得できたソースと、失敗・未接続のソースを `## 今日の予定` の直下に必ず書く。** 書式は `（取得元: Google ✓ / Outlook 未接続）`。
5. イベントの `attachments[]` は `title` を持つのでそれを表示名に使い `[title](fileUrl)` 形式で `## 資料` に書く。`description` 内の裸のURLは表示名が得られないのでURLをそのまま貼る。

第4項は必須である。取得できていない事実が毎日デイリーノートに現れることで、連携の欠落が放置されるのを防ぐ。

## ノートの編集

- `status` や `due` の変更は frontmatter を直接編集する。値域は `.claude/CLAUDE.md` の表に従う。
- `task` を完了にするときは `status: 4_done` と `done: <今日の日付>` を両方書く。
- `context` を1件だけ直す場合は、そのノートの frontmatter を直接編集する。**同じ値を持つ他のノートも直す必要がある場合は、`rename_context.py --old` で一括付け替える。** AIが新しい `context` を自分で決めてノートを作る運用のため、1件を手で直しても同じ値を持つ他のノートは古い値のまま残り、`index.py --contexts` が誤った値と正しい値の両方を返し続けてしまう。`context` が空のノートに後から値を付ける場合（規則2の発火時など）は `--old ""` が使えないため `rename_context.py --path` を使う。
- `## 更新履歴` は作らない。`project` の `## 経緯` にだけ、方針・判断の変化を書く。`status` の変更では書かない。

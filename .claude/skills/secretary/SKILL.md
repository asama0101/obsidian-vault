# secretary

Obsidian vaultで秘書業務を回す。人間との接点は `Today.md` 1枚だけ、`Cabinet/Notes/` の一覧取得は `index.py` だけ、分類基準はこのファイルだけ。

## モードの判別

締めと取り込みは `Today.md` の有無と直交するため、先に判定する。

- 「締めて」「クリアデスク」等の明示指示 → **締めモード**
- 会話にメール・チャット等の本文が貼られている → **取り込み**
- どちらでもない場合、`Today.md` の有無と frontmatter の `date` で判定する。
  - 無い → **開始モード**
  - あり、かつ `date` が今日 → **更新モード**
  - あり、かつ `date` が今日でない → **停止する。** 前日分が締められていない。人間に「`<date>` 分の `Today.md` が残っている。`/close` で締めてから `/today` を実行すること」と報告し、自動では先へ進まない。前日の締めが `main` への fast-forward マージ失敗で止まっていた場合は、`/close` を再実行しても同じ地点で再び失敗するため、先に `main` 側を解決する必要があることも併せて伝える。

`date` の照合が要るのは、締めが失敗した翌朝に更新モードへ落ちると、昨日の日付のファイルに今日の予定を書き込み、締めで `Cabinet/Diary/<昨日>.md` として2日分が1ファイルに混ざるため。通知を行わない設計なので、人間はこの混入に気づけない。

締めは時刻では起動しない。人間が退勤したかを時刻から推定できないため。

## 共通の前提

- ノートを作成・編集する前に、日次ブランチ `daily/<今日の日付>` にいることを確認する。無ければ `main` から `git checkout -b daily/<今日の日付>` で作る。
- 日中はコミットしない。締めが1コミットにまとめる。
- `Cabinet/Notes/` を1件ずつ読んではいけない。一覧が要るときは必ず `index.py` を使う。個別のReadは、実際にそのノートを編集するときだけ行う。
- 通知は一切行わない。伝えたいことは `Today.md` に書く。

## Today.md の行書式

更新モードは `## 今日の予定` と `## 今日のタスク` を毎回全置換で再生成するため、書式を固定しないと出力が日々揺れる。

- `## 今日の予定`: `- HH:MM-HH:MM [[議事録ノート名]]`。終日予定は時刻を `終日` とする。セクション末尾に `（取得元: ...）` の1行を置く。チェックボックスは使わない。予定にチェックを入れても意味を持たせる先が無いため。
- `## 今日のタスク`: `- [ ] [[タスクノート名]] <状態>`。`<状態>` は `期限 今日` / `期限超過 N日` / `進行中` のいずれか。ここだけはチェックボックスを使う。人間がチェックした行を更新モードが完了の合図として読むため。
- `## 確認したいこと`: `- <質問>（N回目） →`。
- `## メモ`: 人間の自由記述。処理済み行は元の文言の後ろに ` → [[ノート名]]` を足す。`context` を新規に提案した場合は ` → [[ノート名]]（context: 提案値）` となる。

### 処理済みマーカーの判定規約

`## メモ` の行が処理済みかどうかは、**行内に `→ [[...]]` を含むかで判定する。行末では判定しない。** `context` を提案した行は行末が `（context: 提案値）` になるため、行末で判定すると毎サイクル未処理と誤判定され、同じ行から何度もノートを作ろうとして `new_note.py` が同名衝突で終了コード1を返す。

`- 前日の未処理:` で始まる繰越行は処理対象外とする。開始モードがAIの都合で書いた行であり、人間の依頼ではないため。未処理件数にも数えない。

## スクリプト

```bash
# 索引（列: path type status due done context date title mtime calendar_event_id calendar_series_id、ヘッダ行なし、11列）
python3 .claude/scripts/index.py [--type task,meeting] [--status 1_todo,2_doing] \
    [--date 2026-09-07] [--updated-on 2026-09-07] [--contexts]

# ノート生成（vault相対パスを標準出力に返す。既存なら終了コード1）
python3 .claude/scripts/new_note.py --type task --title "見積書の作成" \
    --set due=2026-09-10 --set context=A社

# 締め（Diary退避・コミット・ffマージ・push）
bash .claude/scripts/close_day.sh
```

## 開始モード

1. 日次ブランチを確認・作成する。
2. `Cabinet/Templates/today.md` から `Today.md` を作り、`date` を今日にする。
3. `Cabinet/MEMORY.md` を読む。
4. 前日の `Cabinet/Diary/<前日>.md` に未処理の痕跡（`- ⚠ 未処理 N件` の行）があれば、`## メモ` に `- 前日の未処理: [[Cabinet/Diary/<前日>]]` の1行を書く。取りこぼしを翌日に繰り越して見えるようにするため。
5. カレンダーを取得する（下の「カレンダー」参照）。
6. 各イベントを `index.py --type meeting --date <今日>` の出力の `calendar_event_id` 列と照合し、一致が無ければ `new_note.py --type meeting --title "<今日の日付> <会議名>" --set calendar_event_id=<イベントのid> --set calendar_series_id=<recurringEventId>` で作る。ノート名は `YYYY-MM-DD 会議名` とする（定例会議は毎回同じイベント名を持つため、日付を含めないと2回目の生成が同名衝突で終了コード1になる）。イベントに `recurringEventId` が無い（単発イベントである）場合は `--set calendar_series_id=...` を渡さず、`calendar_series_id` は空のままにする。`## 資料` をイベントから埋める。
7. 定例（`calendar_series_id` が一致）は前回の同シリーズ議事録から `## アクション` の未完分と `## 議題` を転記する。当日の会議が3件以上を目安に、各会議の過去議事録探索を Explore サブエージェントへ並列委任する。探索範囲は `Cabinet/Notes/` のみ。書き込みは自分が行う。並列委任を行うのは開始モードだけとする（更新モードは30分ごとに走るため、サブエージェントの起動は過剰になる）。
8. `index.py --type task --status 1_todo,2_doing` を叩き、`due` が今日以前のもの、または `status` が `2_doing` のものを今日のタスクとする。
9. `## 今日の予定` と `## 今日のタスク` を書く。
10. `/loop` を30分間隔で起動し、更新モードを自走させる。

## 更新モード

1. 必要な索引を `index.py` で取得する。**個別ノートを1件ずつ読んではならない。**これが本来の制約であり、呼び出し回数そのものではない。1サイクルの `index.py` 呼び出しは数回に収め、ノート件数に比例させない。
2. カレンダーを1回だけ引く。以降のステップは取得済みのイベント一覧を使い回す。
3. `Cabinet/MEMORY.md` を読む。分類と `context` の推定に使う。
4. **`## 今日のタスク` のチェック済み行（`- [x]`）を完了の合図として扱う。** 対応するタスクノートの `status` を `4_done`、`done` を今日の日付にする。状態はノート側の frontmatter が持つため、次のステップの全置換で当該タスクは一覧から外れる。冪等性は保たれる。
5. **カレンダーに新しく現れたイベントの議事録ノートを作る。** 開始モードのステップ6と同じ照合・生成を行う（`index.py --type meeting --date <今日>` の `calendar_event_id` 列と照合し、無ければ `new_note.py` で作る）。定例なら前回の同シリーズ議事録から `## アクション` の未完分と `## 議題` を転記する。**ここでは Explore への並列委任は行わない。** 日中に会議が追加されたとき `## 今日の予定` にリンクだけが並んで実体が無い状態を作らないため。
6. **会議のキャンセル判定を行う。** 対象は `index.py --type meeting --date <今日>` が返す行のうち `status` が `1_予定` のものだけに限る。そのうち `calendar_event_id` が今日のカレンダーに存在しないものを `3_中止` にする。**`date` が今日でない過去の議事録には絶対に触れない。** このモードは前回状態を保存しないため、対象を今日かつ `1_予定` に絞らないと「今日のカレンダーに無い」＝「過去の全議事録」となり、30分ごとに過去の記録を書き換えてしまう。
7. `## 今日の予定` と `## 今日のタスク` を**全置換で再生成**する。開始モードと同じ抽出条件を使う。ステップ4〜6でノートの状態を先に確定させてから書くため、リンク切れも完了済みタスクの再掲も起きない。
8. `## メモ` の未処理行を分類し、`new_note.py` でノート化し、行の後ろに ` → [[ノート名]]` を追記する。未処理行とは、上の「処理済みマーカーの判定規約」に従い**行内に `→ [[...]]` を含まない行**である。`- 前日の未処理:` で始まる繰越行は処理対象外とする。
9. `## 確認したいこと` の回答済み行（`→` の右に文字がある行）を処理し、ノート化してその行を削除する。元になった `## メモ` 行があれば、その行の後ろにもリンクを追記して未処理状態を解消する。
10. **終了時刻を過ぎた会議の事後構造化を行う。** `## メモ` の生メモから `## 決定事項` と `## アクション` を抽出して議事録ノートに書き、アクションはタスクノートとして起票して議事録からリンクする。`status` を `2_実施済` または `4_不参加` に更新する。判断がつかなければ `## 確認したいこと` へ回す。

このモードは冪等である。前回の状態を保存する必要はない。

`## メモ` と `## 確認したいこと` に対しては追記と処理済み行の削除だけを行い、人間が書いた文言を書き換えない。

## 締めモード

1. `index.py --updated-on <今日>` と `Today.md` の内容から、`Cabinet/MEMORY.md` へ昇格すべき持続的文脈があるか判断する。あれば `- <内容>（YYYY-MM-DD 記録）` の形式で1行追記する。
2. `## 今日の予定` と `## 今日のタスク` を当日の実績サマリーに書き換える。`## 確認したいこと` と `## メモ` は変えない。
3. **未処理の棚卸しを行う。** 未処理のメモ行（「処理済みマーカーの判定規約」に従い**行内に `→ [[...]]` を含まない行**。`- 前日の未処理:` で始まる繰越行は数えない）または未回答の確認事項（`→` の右が空の行）が残っている場合、`## メモ` の先頭に `- ⚠ 未処理 N件（内訳: メモ X件 / 確認 Y件）` の1行を追記する。
4. `bash .claude/scripts/close_day.sh` を実行する。
5. **`/loop` を停止する。`ScheduleWakeup` ツールを `stop: true` で呼ぶ。** 成否にかかわらず停止する。失敗は人間の介入を要する状態であり、自動処理を続ける理由が無いため。

未処理のメモ行や未回答の確認事項は、上のサマリー行を足したうえで `Today.md` ごと `Cabinet/Diary/` へ退避する。強制的なノート変換は行わない。翌朝の開始モードが前日の Diary にこの `- ⚠ 未処理` 行を見つけると、新しい `Today.md` の `## メモ` に繰越の1行を書く。取りこぼしが黙って消えないようにするための最小限の仕掛けである。

## 取り込み

会話に貼られた本文からノートを作る。

1. 依頼内容・締切・関連する案件を読み取る。
2. 下の分類基準で `type` と `context` を決める。旧 `setup` スキルが担っていた新規プロジェクトの起票もこの経路に含まれる。「〇〇案件を起票して」のような指示は、分類基準で `project` と判定して `new_note.py --type project` を実行する経路になる。
3. `new_note.py` でノートを作り、原文全体を `task` なら `## 作業ログ`、`project` なら `## 概要`、`meeting` なら `## メモ`、`know-how` なら `## 状況` に残す。
4. 作ったノートのパスを人間に伝える。

## 分類基準

判定順に評価し、最初に該当したものを採る。

1. **meeting** — カレンダーイベントに対応する、または会議・打合せの記録である。
2. **project** — 複数のタスクを束ね、数週間以上続き、固有名詞で呼ばれる案件である。
3. **task** — 期限または完了条件があり、自分が行う具体的な行動である。
4. **know-how** — 再利用可能な手順・知識であり、行動ではなく参照対象である。

判断にあたっては `Cabinet/MEMORY.md` を参照する。関係者の役割や継続中の前提が書かれており、特に `context` の推定に効く。

`context` は `index.py --contexts` が返す既存値から選ぶ。**既存値に該当が無い場合は、新しい `context` の候補を自分で決めてノートを作る。確認事項には回さない。** `## メモ` の該当行には ` → [[ノート名]]（context: 提案値）` の形で提案したことを示す。人間が違うと思えば次の指示で直せばよい。この注記が行末に付くため、処理済みの判定は行末ではなく行内で行う（上の「処理済みマーカーの判定規約」を参照）。

既存値が少ない運用初期に「該当が無ければ確認事項へ」とすると、ほぼ全てのメモが質問に化けて往復が発生する。AIが提案して人間が却下する向きにしておく方が運用が続く。

### 確信が持てないとき

`## 確認したいこと` に `- <質問>（1回目） →` の形式で1行追加する。回数は行そのものに書く。更新モードは冪等で前回状態を保存しないため、往復回数を数える場所は `Today.md` の行自身以外に無い。

回答が曖昧で再度聞く必要がある場合は `（2回目）` として書き直す。**往復の上限は2回とする。2回目でも確定しなければ、最も確からしい分類でノートを作り、その旨をノート本文に1行記す。** 人間とAIの往復を無限化させないため。

同じ内容の質問が `## 確認したいこと` に既にある場合は追加しない。更新モードは30分ごとに走るため、重複防止が無いと同じ質問が1日に何度も積み上がる。

## カレンダー

1. 実行時に利用可能なカレンダーMCPツールを列挙する。
2. 見つかったすべてのソースから当日 00:00–23:59（ローカルタイムゾーン）のイベントを取得してマージする。
3. イベントの `id` を `calendar_event_id`、`recurringEventId` を `calendar_series_id` に対応させる。
4. **取得できたソースと、失敗・未接続のソースを `## 今日の予定` の直下に必ず書く。** 書式は `（取得元: Google ✓ / Outlook 未接続）`。
5. イベントの `attachments[]` は `title` を持つのでそれを表示名に使い `[title](fileUrl)` 形式で `## 資料` に書く。`description` 内の裸のURLは表示名が得られないのでURLをそのまま貼る。

第4項は必須である。取得できていない事実が毎日 `Today.md` に現れることで、連携の欠落が放置されるのを防ぐ。

## ノートの編集

- `status` や `due` の変更は frontmatter を直接編集する。値域は `.claude/CLAUDE.md` の表に従う。
- `task` を完了にするときは `status: 4_done` と `done: <今日の日付>` を両方書く。
- `## 更新履歴` は作らない。`project` の `## 経緯` にだけ、方針・判断の変化を書く。`status` の変更では書かない。
